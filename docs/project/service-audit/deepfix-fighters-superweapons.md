# Fighter, bomb, superweapon and capital combat audit

Status: the fighter activation notification-order defect is fixed with a focused regression test. The broader audit remains incomplete; this note is a partial handoff, not a completion record.

## Verified client flow: fighter ability activation

The V24.01 client exposes three activation modes. `FightersSvc.ActivateAbilitySlotsOnTarget` checks safety, calls `_ActivateAbilitySlots(..., targetID)`, then registers successful targets (eve-logic `eve/client/script/parklife/fightersSvc.py:158-175`). Self and point activation use the same RPC helper, with the point sent as an argument (`fightersSvc.py:177-186`); positional aiming calls this at `positionalControl.py:166`. The common helper calls `fighterMgr.CmdActivateAbilitySlots`, reports returned per-fighter errors, and signals pending activation only for success (`fightersSvc.py:187-199`). Deactivation follows the same per-fighter error / pending pattern (`fightersSvc.py:200-212`).

The client consumes the resulting state in `ShipFighterState`: pending and activated events update active status, charge count, cooldown and UI signals (`eve/client/script/ui/inflight/squadrons/shipFighterState.py:147-165`); deactivation clears ability targets and surfaces a failure reason (`shipFighterState.py:166-182`). Ability targets are consumed by target brackets and tactical navigation (`targetInBar.py:490-525`, `tacticalNavigation/actionDisplay.py:165`). Full state is loaded through `GetFightersForShip` during ship state refresh (`shipFighterState.py:202-229`).

A client-side safety-check detail needs a server-side counterpart: the target activation method calls `_CheckSafetyLevelForAbility(fighterID, abilitySlotID)` without its available `targetID` argument (`fightersSvc.py:168`; the optional parameter defaults to `None`, lines 143-149). EveJS resolves the target and performs target-specific safety validation (`server/src/services/fighter/fighterRuntime.js:4288-4320`). eve.rs's `SpaceFighters` activation path validates target presence/type and builds the effect (`dotnet/src/Eve.Services.Space/SpaceFighters.cs:199-271`), but its constructor has no crimewatch dependency (`SpaceFighters.cs:51-82`). This is a parity concern that still needs authoritative crimewatch and simulation checks before it can be called a proven defect or fixed safely.

## Fighter point ability implementation comparison

EveJS `ActivateAbilityEffectOnPoint` requires the selected point, then starts the effect with no item target; the ability runtime retains the point for the bomb cycle (`server/src/services/fighter/fighterRuntime.js:3037-3156`). eve.rs mirrors the behavior-tree action: `crates/eve-behaviors/src/trees/fighters.rs:74-160` monitors start/stop messages and aligns before activation; `crates/eve-behaviors/src/actions/fighterabilities.rs:95-102` requires the point but invokes the effect with `None`. This matches the EveJS action shape, but it does not establish that bomb damage is implemented in eve.rs.

EveJS's fighter bomb cycle resolves the bomb type and blast radius/damage from type attributes, applies damage to eligible entities around the stored target point, and records combat notifications and killmail damage (`fighterRuntime.js:3037-3156`). eve.rs implements the Host effect in `dotnet/src/Eve.Services.Space/Effects/FighterAbilityEffects.cs:13-20,152-173`, reads bomb type attribute 2324 and SDE damage/radius in `dotnet/src/Eve.Services.Space/SpaceFighters.cs:256-265`, then sends `SimAction.Blast`; the simulation applies it at cycle end in `crates/eve-space/src/modules/effects.rs:133-135` and `crates/eve-space/src/deployable.rs:1326-1350`. `FighterLaunchBombTests` covers Host input, attributes, security refusals and the sim action. EVE University describes fighter bombs as 30 km range, 12 s flight time and 15 km damage radius ([Fighters](https://wiki.eveuniversity.org/Fighters)); the listed implementation sets the action duration from the ability's cycle (60 s for the Hornet test). Whether this is the bomb's flight path or only the fighter ability window has not been reconciled with client timing evidence.

## Defect fixed: fighter ability notice ordering

The V24.01 client records activation as pending only after `CmdActivateAbilitySlots` returns (`eve/client/script/parklife/fightersSvc.py:187-198`), then consumes `OnFighterAbilitySlotActivated` to replace pending with the running state (`eve/client/script/ui/inflight/squadrons/shipFighterState.py:147-165`). EveJS queues that notice with `setImmediate` (`server/src/services/fighter/fighterRuntime.js:2251-2263,2333-2353`). eve.rs previously used `Task.Run` plus a fixed 50 ms delay in `SpaceFighters.Later`, which could elapse before the RPC response under load and let the client process activation before pending. `ClientSession.AfterResponse` queues the action for `PacketDispatcher` to run after `SendCallResponse` (`dotnet/src/Eve.Services/ClientSession.cs:157-180`, `dotnet/src/Eve.Services/PacketDispatcher.cs:253-254`). Activation and request-driven deactivation now use this callback. The Host test asserts no packet is sent until `RunAfterResponse`.

## Verified client path: positional superweapon targeting

The whole-client search found the two `superWeaponMgr` callers in `positionalControl.py`: `_StartTargetedEffect` sends `(moduleID, effectID, destination)` at lines 111-114, and `_StartSlasherEffect` sends `(moduleID, p0, p1)` at lines 117-120. `_GetModuleBehavior` reads the module's shape, max range, fixed-range flag and AOE range/radius to choose the targeting indicator (`positionalControl.py:122-137`). Host composition wires both RPC callbacks to `SuperWeaponService` when the space service exists (`dotnet/src/Eve.Host/Hosting/HostComposition.cs:232-236`) and passes them into `CoreServices` (`HostComposition.cs:257`); the service decodes points and calls the shared module activation path (`dotnet/src/Eve.Services.Space/SuperWeaponService.cs:19-58`). It reports success only after that path returns `Ok`, and maps refusal through `ModuleRefusals`. The client contains no extra local success transition in these handlers: it calls the RPC from the targeting controller and returns (`positionalControl.py:111-120`). EveJS has corresponding RPC handlers in `server/src/services/ship/superWeaponMgrService.js:73-125`; its effect runner is `server/src/space/modules/superweapons/superweaponRuntime.js`. This confirms player superweapon activation is wired; this pass did not compare all per-weapon effects, timers, restrictions or client-visible error strings end to end.
