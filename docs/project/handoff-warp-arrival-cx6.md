### Root cause and why it escaped

An accepted warp sets the Host's `_warping` flag (`dotnet/src/Eve.Services.Space/SpaceSessions.Movement.cs:249-254`). The Rust simulation emits `SimArrived` only when a belt is found (`crates/eve-space/src/scene/mod.rs:1093-1099`); its far-from-belts regression explicitly expects no arrival message (`crates/eve-space/src/scene/tests.rs:1774-1786`). A planet warp therefore completed with the ship's `Stop` action but left Host state set, so later Host admission checks continued to treat the pilot as in warp. The fix observes the own ship's `Stop` in `DoDestinyUpdate` and clears that session's flag (`SpaceSessions.cs:928-945`); `OnLost` clears the flags and returns pilots to a station when the simulation link drops (`SpaceSessions.cs:1055-1129`).

The old Rust test covered the simulation's belt-only arrival event; Host tests did not connect a non-belt `Stop` update to `IsWarping`. The old slow client test requested state during travel (`tools/headless-client/tests/test_warp.py:94-101`) but did not issue a second warp and dock after arrival. CI ran those separate checks, but none asserted the cross-layer invariant that a planet arrival clears Host admission state before the next command. Review likewise evaluated the simulation's belt-arrival contract and the Host's existing message handling independently; it did not walk the resulting state into a subsequent warp or dock call. The Host regression now verifies that another ship's `Stop` leaves the flag set and the pilot's own `Stop` clears it (`dotnet/tests/Eve.Services.Space.Tests/SpaceServiceTests.cs:1512-1531`).
