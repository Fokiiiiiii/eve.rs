## Behavior comparison and correction

- EveJS 261028.1 `addFleetFinderAdvert` replaces the advert, sets `isRegistered`, and notifies fleet members with `OnFleetOptionsChanged` on every Add, even when the fleet was already registered (`server/src/services/fleets/fleetRuntime.js:2778-2791`). The proxy returns the advert payload (`fleetProxyService.js:31-34`).
- Host registers the callback and member-session resolver in `dotnet/src/Eve.Host/Rpc/FleetRpc.cs:65-70`. The persisted advert mutation commits before `FleetProxyService.MutateFleetAdvertAsync` emits member notifications (`dotnet/src/Eve.Services.Space/FleetStore.Adverts.cs:41-46, 177-190`; `FleetProxyService.cs:117-131`).
- Defect: eve.rs previously sent `OnFleetOptionsChanged` only when `isRegistered` toggled. Re-registering to edit an active advert therefore omitted the event the reference server sends. The proxy now sends it for every successful Add, and retains the toggle check for other operations.
- The PostgreSQL regression drives the real `FleetProxyService` call path, decodes notifications from each member session, and checks both initial registration and editing an existing advert (`dotnet/tests/Eve.Services.Space.Tests/SpaceServiceTests.cs:4464-4590`). Against the old condition, the second Add failed at the member notification assertion; with the fix, it passes.

## Fleet Finder join path (code review)

- The panel's Join action calls `FleetSvc.ApplyToJoinFleet`, then logs the join attempt (`fleetfinder.py:363-375`). The client refuses an already joined target with `FleetYouAreAlreadyInFleet`, confirms leaving a different fleet, sets `expectingInvite`, calls `fleetProxy.ApplyToJoinFleet(fleetID, autoAccept)`, and shows `FleetApplicationReceived` only when the result is true (`fleetSvc.py:1897-1911`).
- The next client transition is notification-driven: `OnFleetInvite` uses `fleetID`, `inviteID`, message name and `autoAccept` to accept, prompt or reject (`fleetSvc.py:1176-1199`); approval requests instead arrive as `OnFleetJoinRequest`, which opens the leader's join-request window (`fleetSvc.py:1353-1358`).
- EveJS checks that the advert is registered/open and below its advertised limit; for approval it sends the boss `OnFleetJoinRequest` and returns true, otherwise it sends an invite with the caller's `autoAccept` choice and returns false (`src/server/src/services/fleets/fleetProxyService.js:22-27`; `fleetRuntime.js:2885-2943`). eve.rs does the corresponding checks and result/notification paths in `FleetProxyService.ApplyToJoinFleet` (`dotnet/src/Eve.Services.Space/FleetProxyService.cs:9-66`). User-facing errors are `FleetNotFound`, `FleetNotAllowed`, `FleetTooManyMembers`, `FleetError`, and `FleetNoPositionFound`; the client displays returned RPC user errors and handles successful invite/request transitions through notifications. No join-path mismatch was confirmed in this review.

## Local chat state and departure notification fix

- The V24.01 client toggles between the migrated local-chat channel and the legacy XMPP player count. On feature-flag changes it asynchronously opens or closes the local channel and tells `XmppChat` about migration state (`chat/client/chat_service.py:89-97, 205-226`). The local channel resets membership on character/system changes and delays membership for wormhole-style systems (`chat/client/local_chat/channel_controller.py:80-131, 136-180`).
- The messenger subscribes to `LeaveNotice` and forwards it to the local channel controller (`chat/client/local_chat/messenger.py:39-53`). `_on_exit_notice` removes the named member whenever the notice is for the current system (`channel_controller.py:272-285`); therefore sending this notice for a hidden, silent occupant exposes that character's presence to every client in the system.
- Host registers `LocalChatGateway` in `HostComposition.cs:181-183`. It excludes delayed-system occupants from join notices and membership snapshots until they speak (`dotnet/src/Eve.Host/PublicGateway/LocalChatGateway.cs:186-203, 275-287`). Before this fix, `LeaveSystem` sent a leave notice for every departure. It now sends the leave and following membership refresh only for immediate-local pilots or delayed-local pilots that were in the speaker set (`LocalChatGateway.cs:208-228`). This preserves the existing visible-speaker leave order.
- EveJS 261028.1 follows the same rule: `forgetLocalSpeaker` emits `local-leave` only when it actually removed a speaker (`src/server/src/_secondary/chat/chatRuntime.js:1483-1498`), and `unregisterSession` emits a delayed local leave only when `delayedLeave` is true (`chatRuntime.js:1656-1671`).
- The Host regression first failed against the old unconditional leave path. The focused test now drains setup traffic, proves a silent wormhole departure produces no notice, and the adjacent speaker test asserts `MessageBroadcastNotice`, then `LeaveNotice`, then the updated `MembershipListNotice` (`dotnet/tests/Eve.Host.Tests/LocalChatGatewayTests.cs:53-105`). The full `LocalChatGatewayTests` class and the adjacent XMPP delayed-local test passed on `eve_p6` (10 passed, 0 skipped).
