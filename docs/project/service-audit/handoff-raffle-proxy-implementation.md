# raffleProxy implementation handoff

The raffle service is composed with PostgreSQL item, wallet, account and scheduler foundations. Creation validates the pinned SDE type lists and client singleton rules, escrows one eligible item under its owner at the station using flag 178, and consumes HyperCores atomically. The type-list evaluation follows the client expansion of included and excluded type, group and category sets. It uses lists 36 and 142 for trade restrictions and lists 133 and 134 for raffle and singleton validation. Existing system-owned escrow records are migrated transactionally when their persisted custody matches the legacy record.

Ticket purchases lock the raffle and perform wallet, ticket and settlement changes in one transaction. Random bulk calls persist a session, actor and call-ID operation record with its raffle, requested count and selected tickets in the same transaction. A replay returns the prior result without another debit; a different call ID can make a distinct purchase. Award and expiry release the same escrowed item, and expiry refunds ticket holders. Scheduler recovery reconstructs pending expiry jobs. After a committed expiry, current subscribers receive `OnRaffleFinishedServer(raffle_id, None)`; a failing notification sink does not prevent delivery to the other subscribers. Session closure removes the exact session from subscription maps.

The implementation corrects several observed reference or initial-implementation gaps: a fixed category allowlist rejected supported category-7 modules; EVE client field names can arrive as byte strings; an unqualified `owner_id` in the finished-ticket join failed after a committed sellout; and repeating a random purchase with the same Macho call ID previously purchased more tickets. Insufficient funds now returns `NotEnoughISKError`. The supported-item determination comes from the pinned client and SDE rather than the earlier reference category list. The CCP article and client/SDE evidence are recorded in `raffle-client-mechanics-audit.md`.

## Focused validation

The following tests were run separately against local PostgreSQL containing the pinned build 3396210 SDE and build 3405148 mission SDE. Each invocation reported one passed test and zero failures. The Host project compiled as part of the test builds. No full suite was run.

- `dotnet/tests/Eve.Host.Tests/RafflePersistenceTests.cs:Migration_create_sellout_award_and_expiry_preserve_custody_and_money` exercises migration twice and legacy escrow recovery; published module acceptance and type-list exclusion; stack and contained-item rejection; protected escrow destinations; buyer concurrency and insufficient funds; sellout, repeated ticket, award, refund, scheduler restart and expiry; exact finish notification arguments, failed-sink isolation and no duplicate on scheduler replay; and populated filters, metadata, history and statistics.
- `dotnet/tests/Eve.Host.Tests/RaffleCompositionTests.cs:Host_composition_registers_raffle_proxy_with_persistent_callback` builds the actual Host composition on the isolated `eve_raffle_host` database and dispatches encoded requests through its registry. It checks real account-ban state, create and award, random bulk sellout, insufficient-balance rollback and error, same-call replay, conflicting call payload and distinct-call purchase, subscription/unsubscription delivery and `ClientSession.Close` cleanup. The last focused run after the close cleanup passed 1/1.
- `dotnet/tests/Eve.Host.Tests/RaffleHostWireTests.cs:Raffle_proxy_registered_route_reads_real_postgres_raffle_and_returns_wire_error` exercises a manually registered real PostgreSQL raffle service over the Host TCP test transport. It checks populated browse and both FilteredGrab keyword forms, GetRaffle, ticket purchase/retry and notifications, populated active tickets and statistics, and two-page history using `running_id`.

The tests run separately because the composition fixture temporarily changes process environment variables; it restores them in `finally`. The composition database was populated using `tools/dev/copy-sde-database.py` from the local pinned SDE, rather than synthetic static data. Coverage rows RPC-02188 through RPC-02205 identify the passing route-specific test and distinguish encoded composition dispatch from the manually registered TCP boundary.

The current `RaffleCompositionTests.Host_composition_registers_raffle_proxy_with_persistent_callback` additionally injects a failed notification sink before a successful bulk purchase. Before the fix, the committed purchase returned an ErrorResponse and stopped later delivery; after per-recipient isolation, it returns CallRsp, the later subscriber receives its two notifications, and replay neither debits nor notifies again. The focused test passed 1/1 against actual Host composition and PostgreSQL. Creation and award notifications use the same failure isolation.

The creation path also resolves the station and solar system from the pinned SDE `npcStations` and `mapSolarSystems` records. It rejects non-NPC locations, a supplied `solar_system_id` that differs from the station's system, and Triglavian systems; if the system is omitted it persists the authoritative system. The client checks `IsStation` and `IsTriglavianSystem` in `raffles/client/create/controller.py:289–302`; `eve/common/script/sys/idCheckers.py:140–145` defines the latter using `mapSystemCache.factionID == factionTriglavian` (500026). The pinned SDE can omit factionID for Pochven systems, so the server also rejects region 10000070, consistent with the existing `MoonRulesSource` Pochven authority. The client's compiled `systems.static` cache was not available for a direct comparison of every system; the region fallback is therefore documented separately from the exact client faction predicate.

`RaffleStationValidationTests.CreationRequiresAnNpcStationAndItsAuthoritativeNonTriglavianSystem` first failed against the previous implementation because it accepted a structure as a station. After the fix it passed 1/1 against PostgreSQL and the pinned SDE, checking structure, Pochven and mismatched-system rejection without consuming the prize or tokens, and valid Jita creation with the system derived when omitted. The existing `RaffleCompositionTests.Host_composition_registers_raffle_proxy_with_persistent_callback` encoded Host registry regression also passed 1/1 after the change.

`RafflePriceRuntimeTests.RuntimeGlobalPriceAndFractionalDivisionDetermineActualTokenConsumption` exercises actual Host composition, administrator runtime `HyperNetPlexPriceOverride` writes and encoded creation requests. Before the fix, an override of 11 left 99 of 100 HyperCores where the client calculation requires 55; afterwards the test passed 1/1, including totals 1099.92 and 1100 around the truncation boundary and an override of -1. `raffles/common/util.py:7–18,21–35` uses true division and evaluates `int(total_price / max(1, plex_price / 10) * BROKERS_FEE)`. The server now reads the current override through the composition callback and follows that operation order.

When `HyperNetPlexPriceOverride` is zero or absent, the client uses the PLEX average it received through `config.GetAverageMarketPrices`, which it caches after startup. The server records the same wire `double` for that session only after sending a successful response, and uses it for the creation fee; a later market change does not silently alter that client's quoted fee. The same focused test passed with real PostgreSQL fills changing from 11 to 20 after the encoded config response: creation used the advertised 11, another session did not inherit it, and a missing snapshot was rejected before item or token mutation. The client's LOCAL preference is not available to the server; absent an advertised price the server rejects creation rather than assuming the client's local fallback.

The client obtains the override with `int(global_config.get('HyperNetPlexPriceOverride', 0))` (`raffles/common/util.py:32–36`): a finite numeric value is truncated toward zero, while a non-integer string fails conversion. The focused `RafflePriceRuntimeTests` additionally passed with actual runtime `PyReal` overrides of 11.5 and -1.5, verifying the corresponding 11 and -1 token calculations. The host currently accepts finite floating overrides only within the signed 64-bit integer range; Python integers are not restricted to that range. Values outside it follow the existing unparseable-override fallback. The shared Host.Tests build completed with zero warnings and zero errors under the Tourney owner's build slot; this focused test was then run separately with `--no-build --no-restore` and passed 1/1.

## Limits

The TCP test assigns the ID of a real PostgreSQL account in the server-side session-open fixture; it does not exercise a full client login. The composition test dispatches encoded packets through the actual registry but does not use TCP. The close test calls `ClientSession.Close` with its sink still attached; HostServer calls that method when its session actor ends, but real socket termination and session-ID reuse were not separately exercised. The unmodified graphical client was not run, and the focused tests do not establish full gameplay or full-suite compatibility. Expiry notifications are sent to current subscribers after commit; network delivery is not exactly-once, and a reconnecting client must refresh authoritative state.
