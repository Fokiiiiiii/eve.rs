# Deviations from the reference server

The reference (EVE.js) is matched by default (`docs/adr/0001-external-compatibility-only.md`).
A deliberate difference goes here, with the evidence that the client cannot tell or that it
is better off, and how it is tested. A behaviour is either:

- **contract**: the client can observe it; eve.rs matches the reference;
- **tolerated**: the client can observe it but accepts a better behaviour; eve.rs may differ,
  and the difference is listed below;
- **internal**: the client cannot observe it; eve.rs is free.

## Register

| # | Behaviour | Reference does | eve.rs does | Evidence | Status |
|---|---|---|---|---|---|
| 1 | Password check at login | Accepts any password by default (`devSkipPasswordValidation` is true) and creates an account on first use | Checks the password hash by default; an unknown user name still creates the account with the hash it presented; `EVE_DEV_SKIP_PASSWORD=1` restores the reference | The client always sends the hash of the password typed, so only a wrong password can tell the two apart (it is refused, as a real server does) | tolerated (S1); `tools/dev/run-eve-live.sh` runs the wrong-password test |
| 2 | Session ids | `ms * 15 + clientID % 15`, which can repeat within a millisecond | The same value, moved up past the last one issued | The client reads `sessionID` as an opaque long; a repeat replaced a live session in the front (found by a test) | internal (S1) |
| 3 | Character slots | The screen says 3 (`maxCharacterSlots`) but nothing stops an account making more: the recording has four on one account | Refuses a character beyond the three, with a `CustomInfo` message; two creations racing for the last slot cannot both win | The limit is stated to the client in the selection data, so a server that keeps it is what the screen promises | tolerated (S2); marked `DEVIATION (slots)` in `tests/test_login_to_character.py` |
| 4 | Reserved names | Reserves the staff prefixes (`CCP `, `GM `, `ISD `) and also "Elysian", the name of its own system character | Reserves the staff prefixes only | Nothing in the client refers to "Elysian"; a player may want it | tolerated (S2); the `Elysian` case of the name test |
| 5 | When two names are one | Names that differ by case or spacing are one name (`recorded pilot` is taken by `Recorded Pilot`) | The same, and names that differ only in Unicode compatibility form (full-width letters, combining marks) are one too (NFKC) | The client shows both spellings alike, so allowing both makes look-alike names | tolerated (S2); `dotnet/tests/Eve.Characters.Tests/NameTests.cs` |
| 6 | Account creation date on the selection screen | A constant (the year 2019) | The time the account was created | The client displays it as the account's age; a real date is what the field means | tolerated (S2) |
| 8 | A character's description | New characters have the text "Character created via EveJS Elysian", the reference's own branding | An empty description | The client shows the description in the character sheet; text that names another project is not something a player wrote | tolerated (S3); the `description` of the public record and `GetCharacterDescription` in `tests/test_login_to_character.py` |
| 9 | Asking about a character or station that does not exist | A made-up id gets a made-up record: `charMgr.GetPublicInfo(1)` returns the name of the last character chosen, `stationSvc.GetStation(1)` returns Jita IV | `None`, as for any call the server cannot answer | The made-up record is a side effect of the reference filling every field with defaults; a real server has no such answer, and the client asks about ids it has been given | tolerated (S3); `dotnet/tests/Eve.Services.CharacterInfo.Tests`, `Eve.Universe.Tests` |
| 10 | What is in a ship | The ship's inventory answers `None` to `List`, `ListByFlags` and `GetCapacity`, and its contents (`GetContainerContents`) list the ship itself | `List`, `ListByFlags`, `GetItems` and `GetContainerContents` list what is fitted to it and carried in it (a new ship: the starter modules), a flag with nothing in it answers the empty `set` a hangar answers with; `GetCapacity` is still `None` (see "Not yet matched") | The client iterates the answer to `List` (`for item in inventory.List(flag)`), which a `None` breaks; a ship does not contain itself | tolerated (S3); `ship_contents` in `tests/test_login_to_character.py` checks the modules against the dogma recording |
| 11 | The character's attributes "as the ship changes them" (`GetAllInfo.shipModifiedCharAttribs`) | Trade premium (443) is 0 for a character that has Trade trained (its own brain says -10% of 1), and the Gallente rookie ship's mining-drone bonus (428) is left out (100) | Every modifier that reaches the character is applied: 443 is 0.9 with Trade at level 2, and 428 is 120 for the Gallente rookie ship | The client's own rules (`dogma/attributes`, the effects of the static data) say so, and the reference's brain and its attribute contradict each other; the numbers are read for market fees and mining-drone yield only | tolerated (S3); the two values are asserted in `ReferenceTests` and replaced in the expectation of `test_a_new_characters_dogma_is_that_of_the_reference` |
| 12 | Drone limits on the ship | A ship's attributes list the character's drone limits: `maxActiveDrones` (352) and `droneControlDistance` (458) | Only the character has them | The client reads both from the character (`GetAttributeValue(session.charid, ...)`, `clientDogmaLocation.py:1436`, `ghostControllerMixin.py:509`); the ship's copy is never asked for | tolerated (S3); replaced in the expectation of `test_a_new_characters_dogma_is_that_of_the_reference` |
| 13 | Starting a skill by its item (`CharStartTrainingSkill(itemID)`) | Looks the item up in its item store, which has no skill items, so it answers `None` and trains nothing | Starts the skill: the item id of a character's skill is its id times 100000 plus the type (the id the client was given in the skill's entry), so it names the skill; an item that is not one of the character's skills starts nothing | The client passes the id of the skill entry it holds; a server that ignores it is a bug, not behaviour (the queue call the current client uses, `SaveNewQueue`, works on both) | tolerated (S3); `Starting_a_skill_by_its_type_or_by_its_item_runs_it_and_anything_else_starts_nothing` in `Eve.Services.Skills.Tests`, marked DEVIATION in `test_the_skill_queue_is_what_the_reference_does` |
| 14 | Which skill shows as training | The first skill of the queue is marked `inTraining` in the skill list even when the queue is paused (after `AbortTraining`, or saved with `activate=False`) | Only a skill that is training is marked; a paused queue marks none | The client shows the flag as "in training" with a running timer; a skill that is not gaining points is not training | tolerated (S3); marked DEVIATION in `view_problems` of `tests/test_login_to_character.py` |
| 15 | Where a ship appears when it undocks | The first of the authored undock points of the station's type that suits the ship's size (`stationGraphicLocators`, taken from the client's graphics; 44 station types), on the station model, facing along the point's direction (rotated by the station's orientation); a station with no such point uses the station's stored dock position | On the line away from the star (along the station's authored orientation where the reference has one, for two stations), at a third of the station's radius from its centre (at least 2 km; the recorded ship left at 0.34 of it), moving away at top speed | The locators are not in the SDE (the reference ships them as a table of its own, made from the client's graphics), so the exact point cannot be reproduced yet; the client only needs a ship near the station and within docking range, as the reference's is (a station's docking range is measured from a sphere of its radius, and the reference's ship starts inside it) | tolerated (S4); `crates/eve-space/src/scene.rs` (`an_undocked_ship_is_put_off_the_station...`, `a_ship_leaves_a_big_station...`), the position, velocity and direction of the ship are the only fields left out of the bind comparison in `scene_matches_reference.rs` |
| 16 | What the system's ballpark holds | Customs offices (ids from 1.2e12) and, one stamp after the state, eight "props" per station (type 3739 to 3741, group 99) that the reference's own data adds | The stations, planets, moons, belts, the star and the stargates of the static data, and the ship | Neither is in the static data; the client draws the bodies it is sent and needs none of them to fly, dock or jump | tolerated (S4); the comparison in `payloads_match_reference.rs` leaves out ids from 1e12 and the props' second `AddBalls2` |
| 17 | How a ship turns | The heading turns in steps of the reference's own turn rule (fast for small ships, slower the more agile the hull is not), while speed follows the carbon integrator | The heading is the one asked for at once; speed follows the carbon integrator as in the reference | The client turns and moves the ball itself from the actions it is sent, and the server's copy is only used to answer `UpdateStateRequest` and to decide whether a ship is close enough to dock; the reference's turn rule is its own approximation, the client's rule is in the native destiny code that cannot be read | tolerated (S4); revisit with warp and combat, where the heading matters to the server (S5) |
| 18 | The bound objects announced at a docking | At an undock and again at a docking it tells the client to let go of every object bound to the session (`OnMachoObjectDisconnect`), the ones it announced before too | Announces each object once: at the undock those of the station, at the docking those bound in space since (`beyonce`) | The client drops an object when told and rebinds when it needs it; a second notice for an object it has dropped changes nothing | tolerated (S4); `collapse` in `tests/test_undock.py` counts the notices as one run |
| 19 | How `beyonce.GetFormations` is cached | Hands out a cache object (`CachedObject`, a pickle of the formations under the proxy's node) that the client fetches from `objectCaching` when it needs it | Answers the formations inline in the `CachedMethodCallResult`, as the reference does for a result it does not cache at the proxy | The client keeps either under the same call for the length of the session; the fetch needs the pickle and the CRC of the client's own Python, which is not worth reproducing for two fixed formations | tolerated (S4); `compare_answer` in `tests/test_undock.py` |
| 7 | A session's `role` | Every account gets the staff roles and a chat colour by default (a development setting), on top of a base mask | The account's role from the identity module (0 for an ordinary player) with the same base mask `0x6000000080000000`; the initial state carries the account's role, the session change on choosing a character carries the combination | The client uses the bits to show staff tools; a normal account should not have them | tolerated (S2); `role` is compared by type only in the differential test |

## Candidates to examine

Each is matched to the reference today. None is decided; the evidence needed is in the last column.

| Behaviour | Why it may not need to match | Evidence to collect |
|---|---|---|
| A handler that throws is answered with a `None` result, not an error | A `None` where the client expects data is probably worse than an error the client can report | What the client does on each service's `None` and on an error response |
| A service call may reach any method of the JS class by name | Only the methods the client calls matter | `docs/spec/services.tsv` against the reference's method set |
| A received `str` is echoed as `buffer` (`JsSemantics.AsReceived`) | The Python 2 client's `str` is bytes, so it may not tell the two apart | The client's marshal reader for opcodes `str` and `buffer` |
| JavaScript number and truthiness rules in ported handlers (`parseInt`, `\|\|`) | They are accidents of the language unless the client feeds the value | Which inputs the client can send |
| `charMgr.GetPublicInfo`'s `empireID` is taken from a table of four corporations (a Caldari school's pupils are shown under the Gallente empire, 500004) and is the faction for every other corporation | The table looks like a mistake; the client reads `empireID` only to pick an empire icon (`RACE_ICONS[empireID]`) | Whether the character sheet gets `empireID` from this record, and which icon a Caldari character should have |
| A station's `serviceMask` and `reprocessingEfficiency` are the same for every station on the reference | The data has the services and the efficiency of each operation; a constant may show services a station does not have | Which of the two the client's station window and reprocessing window rely on |
| The points of a starting skill at level II and IV are rounded (1,414 and 45,254 for rank 1), while the training queue rounds up (1,415 and 45,255) | A skill trained from level I to II ends with 1,415 points while a starting skill of the same level has 1,414; the game rounds up | Whether the client compares a skill's points with its level thresholds (`skillPoints >= threshold`) anywhere it would show a starting skill as a point short |
| Session and cache objects are sent in the reference's order | The client may not depend on the order | A run of the client with the order changed |
| One JSON document per legacy table, with a synchronous cache-first API | It is storage and internal structure | Nothing observable; decided by the design of each domain module |

## Not yet matched

Behaviour of the reference that eve.rs does not have yet, and where it will come from. These are gaps, not
decisions.
