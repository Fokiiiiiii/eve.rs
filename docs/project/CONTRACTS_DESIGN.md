# Contracts design

## Scope and evidence

The V24.01 client has three contract types: item exchange, auction, and courier. Its client code imports the skills `Contracting`, `Advanced Contracting`, and `Corporation Contracting`; it has no `Public Contracts` skill identifier. A loan contract is not in the V24 client type flow. The first implementation slice must follow the client type and skill tables in `eve/common/script/util/contractscommon.py` and `inventorycommon/const.py`, rather than introducing another type or skill.

The startup read is established by V24 `eve/client/script/ui/shared/neocom/contracts/contracts.py:190-205`: `GetLoginInfo()` returns a KeyVal with `assignedToMe` rows (`issuerID`, `contractID`), `needsAttention` rows (`contractID`, `state`), and `inProgress` rows (`contractID`, `startStationID`, `endStationID`, `expires`). EveJS v0.12.9 `contractProxyService.js` and `contractRuntimeState.js` build these from persisted contract records. eve.rs migrates PostgreSQL `contract_records`, `contract_items`, `contract_requested_items`, and `contract_bids`, and wires `GetLoginInfo` and `GetMyContractEscrow` to its read model. The `CreateContract` RPC accepts both the client KeyVal dictionary form and the V24 `contracts.contractStruct.ContractStruct` positional object form (including its 17-field constructor order); it decodes the client's byte-string title and description before validating client terms, availability, station context, corp contract-manager role, skills, and fees before calling the Host writer. The writer stages offered inventory, requested-item terms, and issuer reward escrow, broker fee, sales tax, and deposit with wallet journal entries in one PostgreSQL transaction. An advisory transaction lock serializes outstanding-limit checks per issuer; the PostgreSQL Host tests cover persisted escrow, partial stacks, limit rejection, and rollback on invalid items or insufficient wallet funds. Item-exchange acceptance and auction bidding/buyout now settle through the Host writer. Courier acceptance moves the persisted Plastic Wrap marker to the hauler and escrows collateral; courier completion and failure settle package contents, reward, and collateral transactionally. Outstanding listings schedule durable expiry jobs in the creation transaction. A Host PostgreSQL regression reconstructs the scheduler after creation and executes the persisted due job, then checks the terminal state and replay refusal. Expiry returns offered items and reward escrow; auctions settle a winning bid and item transfer or return escrow when no bid exists. `DeleteContract` locks an outstanding or rejected contract, checks issuer/contract-manager authority, returns offered items and reward escrow, refunds active auction bids, removes the courier wrap, marks the contract deleted, and cancels its pending expiry job in the same transaction. Focused PostgreSQL regressions cover expiry return/replay, winning-auction settlement, deletion refund/job cancellation, and creation journal entries. Contract lifecycle notifications are written to the transactional event outbox and delivered after commit for creation, private assignment, acceptance, courier completion/failure, auction outbid/buyout, and expiry. Corporation-issued creation, acceptance-for-corporation, issuer-side courier failure, and deletion enforce the client Contract Manager role; `ContractProxyServiceTests` covers corporation issue refusal and accept-for-corporation refusal without that role. `ContractNotificationTests` verifies corporation and alliance notification recipient selection. The RPC applies the issuer faction warfare upgrade adjustment for the contract start system to the broker fee. `GetMyBids` now reads outstanding contracts from the caller's persisted, non-refunded personal or corporation bids and returns the contract and escrow item rows. Corporate bid reads require the Contract Manager role. `GetContractListForOwner` applies owner, status, type, issuer, and 100-row cursor filters to persisted contracts. The client `GetMyCurrentContractList` reads the caller's active issuer or acceptor contracts; `GetMyExpiredContractList` reads rejected, failed, and expired outstanding contracts. Corporate reads require the Contract Manager role. `SearchContracts` public/region filtering remains open. The two-character walk now checks the persisted escrow item ID after acceptance; the previous assertion checked the source ID after a partial-stack split, so it observed the issuer’s unoffered remainder. The test also checks that remainder has quantity one. A successful live rerun remains open.

Primary client references: `eve/client/script/ui/shared/neocom/contracts/contracts.py`, `contractsearch.py`, `createContractWnd.py`, and `eve/common/script/util/contractscommon.py` in eve-logic V24.01. The item-exchange writer enforces the UI expiry choices (1, 3, 7, 14, or 28 days), 50-character title and 4000-character description limits, and the 500-item selection cap from `EXPIRE_TIMES`, `MAX_TITLE_LENGTH`, and `MAX_NUM_ITEMS`. Behaviour comparison: EveJS v0.12.9 `server/src/services/_other/contractProxyService.js` and `server/src/services/contracts/contractRuntimeState.js`.

## Persistence and ownership

Use the Host PostgreSQL store as the sole authority. A contract header stores its id, issuer character or corporation, type, availability/assignee, start and end location, create/accept/expiry/completion timestamps, lifecycle status, reward, price, collateral, duration, description, and the escrow ledger amounts. Child rows store each escrowed item snapshot and quantity; auction bids are separate ordered rows keyed by contract and bidder. Keep contract state, item transfers, wallet balance changes, wallet journal rows, and contract notifications in the same database transaction where the existing inventory and wallet providers permit it. Do not maintain a process-local duplicate contract store.

Escrowed items remain real inventory rows in the existing inventory owner/location model, with a contract escrow location or equivalent persisted ownership marker. Creation validates ownership, quantity, location, issuer authority, contract limits, item eligibility, and wallet funds before transferring any item or ISK. Failure rolls the entire operation back. Item-exchange acceptance locks the contract and affected wallet/inventory rows; repeat acceptance by the same actor returns the committed row. The focused PostgreSQL race test submits distinct acceptors simultaneously and checks one winner, one item delivery, one price debit, and one issuer credit. The same regression submits equal opening bids simultaneously and checks one active bid, one debit, and no lost escrow; both paths serialize on the contract row. Auction bid replacement and buyout, item-exchange acceptance, courier acceptance/completion, deletion, and expiry use transactional paths. Contract mutation notifications are published in the corresponding transaction and delivered to connected characters or corporation members after commit.

## Lifecycle

```text
Draft -> Outstanding -> (Accepted -> InProgress -> Finished | Failed | Rejected)
                     -> Deleted
                     -> Expired
Outstanding auction -> Outstanding with bids -> Finished after expiry or buyout
```

Item exchange settles both item and ISK legs on acceptance. The current Host transaction locks the outstanding contract, checks availability and expiry, moves requested items from the acceptor at the contract station to the issuer, moves offered escrow to the acceptor, clears the delivered-item escrow markers, transfers price to the issuer, credits reward, and marks the contract finished. Settlement clears active reward escrow while the separate `reward_isk` term preserves the displayed contract reward; delivered item rows no longer carry the `in_crate` marker. A repeat by the same acceptor returns the existing result. Auction acceptance is a bid, not immediate settlement: the Host transaction locks the outstanding auction, applies the V24 client minimum-increment rule, refunds the previous active bidder, debits the new bidder, and records the bid atomically. A bid equal to the contract collateral buys out the auction immediately, pays the issuer, and transfers the offered items to the buyer in that transaction. Auction expiry settlement locks the contract and winning bid, transfers the offered items to the highest active bidder, credits the issuer, returns the public deposit, and marks the contract finished in the same transaction. An auction without a bid expires and returns its item and reward escrow; its public deposit is forfeited. A courier acceptance escrows collateral and moves its Plastic Wrap marker to the hauler. Successful completion at the destination transfers the package and reward and returns collateral; failure returns the package at the wrap location, forfeits collateral to the issuer, and returns the reward escrow. These paths run in one transaction and remove the wrap marker. Deletion returns offered items and reward escrow, refunds active auction bids, removes an outstanding courier wrap, and cancels its pending expiry job; the creation deposit remains non-refundable. Expiry returns item and reward escrow and forfeits the public deposit when no auction bid wins. A winning auction at expiry pays the issuer, delivers the offered items, and returns the public deposit. Delete and expiry use row locks and idempotent terminal status updates.

## Notifications and wallet journals

The V24 `contracts.py` handlers consume `OnContractCreated`, `OnContractAssigned`, `OnContractAccepted`, `OnContractCompleted`, `OnContractFailed`, `OnContractOutbid`, and `OnContractBuyout`. EveJS 261018.1 routes these events to the contract owner or affected bidder. eve.rs writes each supported mutation notice into the shared PostgreSQL event outbox in the state transaction; the subscriber sends the client notification after commit to the issuer character, assigned character/corporation, affected bidder, or issuer corporation members. Wallet movements use the shared `WalletTransactions` path, so balances and journal rows commit or roll back with the contract mutation. `ContractReadModelTests.Item_exchange_creation_stages_stack_and_wallet_charges_in_one_transaction` asserts the three nonzero creation journal legs, the committed `OnContractCreated` outbox row, and no event after failed creation. `ContractNotificationTests` verifies that corporation and alliance notices select only matching active character sessions.

`Contract Manager` checks gate corporation-issued creation, acceptance for a corporation, issuer-side courier failure, and deletion. These match the client-side checks in V24 `createContractWnd.py`/`contracts.py` and EveJS `contractRuntimeState.js`; there is no separate hangar-take role gate in the contract call path.

## Availability, skills, and limits

Availability in the V24 create flow includes public, private, my corporation, and my alliance. Private contracts target a character or corporation; corporation/alliance availability must resolve membership at the operation boundary and preserve issuer identity separately from the acting character. Corporation contract operations use the V24 Contract Manager role gate before the corporation wallet and hangar are accessed, matching the V24 client and EveJS `contractRuntimeState.js`; the writer also validates station, owner, and requested division flags. Public search is filtered by the client-supplied region/location and query fields; it must not expose private contract rows.

Use the V24 client tables as the exact capacity contract: personal outstanding limit is the direct `NUM_CONTRACTS_BY_SKILL[Contracting] + NUM_CONTRACTS_BY_ADVSKILL[Advanced Contracting]` table sum; corporation-issued capacity uses `NUM_CONTRACTS_BY_SKILL_CORP[Corporation Contracting]`; and the shared corporation-assigned maximum uses `MAX_NUM_CONTRACTS`. `ContractCreationLimits` copies these six-entry tables from `eve/common/script/util/contractscommon.py`; it does not extrapolate a per-level increment. The Host checks the applicable limit inside a per-issuer advisory-locked transaction. The client source does not define a skill named `Public Contracts`; treat that user-facing term as a request for public-contract availability, not an additional skill.

## Fees, deposits, and collateral

EVE University’s [Contracts](https://wiki.eveuniversity.org/Contract) page describes item-exchange, auction, and courier terms and the public/private/corporation/alliance availability choices. V24.01 `contractscommon.py` is the exact fee formula for this client build: broker fee starts at 0.4% (10,000 ISK minimum, 100,000,000 ISK cap before Broker Relations reduction), sales tax starts at 1% (10,000 ISK minimum, 1,000,000,000 ISK cap before Accounting reduction), and public contracts (availability 0) have a deposit of 1% of base (100,000 ISK minimum, 100,000,000 ISK maximum; courier minimum 10,000 ISK). Private, corporation, and alliance availability (1 to 3) have no deposit. Courier costs use a 0.1 multiplier. Each expiry day after the first adds 0.05 percentage points to the broker rate and applies the separate 5% amount multiplier. These contract rules are separate from market broker fee and market sales-tax calculations.

The core V24 formula is implemented in `ContractFeesCalculator` and covered by `ContractFeesCalculatorTests`: it uses `max(price, reward)`, the type cost multiplier, skill reductions, fee minima/caps, the expiry-day broker increment, and private-contract deposit rules. Its `brokerFeeAdjustment` input is required so the caller supplies the client-equivalent system/faction adjustment from `facwarCommon.GetAdjustedFeePercentage` when applicable. Creation must persist the resulting amounts so later skill changes cannot rewrite a settlement. The calculator does not perform wallet charging or determine that adjustment. A deposit is returned on successful completion and on auction expiry with a winning bid. Deletion and expiry without a winning auction bid forfeit the deposit. Courier collateral is separate from the creation deposit: it is secured from the hauler at acceptance, returned on successful delivery, and paid to the issuer on failure. Do not derive collateral from item prices; it is the amount specified by the issuer.

## RPC and notification boundary

The startup response fields above are confirmed. The client callsites establish `CreateContract(contractInfo, confirm=...)`, `AcceptContract(contractID, forCorp)`, `PlaceBid(contractID, bid, forCorp)`, `CompleteContract(contractID, status)`, and `DeleteContract(contractID)`. The broader read path includes `GetContract`, `SearchContracts`, `GetMyContractEscrow`, `CollectMyPageInfo`, item-location/container reads, and bid/history reads. Each response row shape must be copied from the V24 caller and shared contract row types before implementing that RPC. The service-response audit marks several EveJS-only methods with incomplete shapes; those methods stay out of scope until a V24 caller establishes the wire contract.

The supported V24 lifecycle notifications are written to the shared event outbox inside the mutation transaction and dispatched to connected recipients after commit. Payloads carry the contract ID in the client integer type; creation carries no extra argument. The Host regressions cover persisted creation and expiry event order, and the subscriber selects character, corporation, or alliance sessions from the durable recipient fields. The two-character `test_walk_contracts.py` client walk is selectable from `live-slow`; the live result remains open until that workflow completes green.

## Delivery slices

1. **Creation and item-exchange acceptance built:** PostgreSQL contract header, escrow-item, requested-item, and bid tables; Host read wiring; and `CreateContract` RPC wiring for item exchange, auction, and courier terms. Creation validates station context, contract-manager role for corp issuance, availability, expiry, item/request limits, wallet account, fees, and personal/corporation capacity. The V24 fee formula core is unit-tested; the RPC reads the issuer faction warfare upgrade level for the contract start system and applies the 10% per-level broker fee adjustment. A focused RPC regression verifies the system and character passed to that read and the resulting fee. The Host writer escrows offered items and issuer reward, broker fee, sales tax, and deposit, records requested terms, and performs an advisory-locked per-issuer outstanding-count check in the same PostgreSQL transaction. The listed price remains due from the acceptor at acceptance, following EveJS `prepareContractAcceptanceRequest`. The writer persists contract type, courier destination, duration, and collateral, and marks courier escrow items as packages. Courier acceptance moves a Plastic Wrap marker to the hauler and escrows collateral; destination completion delivers package items and pays reward while returning collateral; failure returns the package and forfeits collateral to the issuer. A PostgreSQL regression covers acceptance, failure, and successful destination delivery. Auction expiry settlement is covered by slice 4; full corp hangar authorization remains open; auction bid replacement and buyout are covered by slice 4. `AcceptContract` is wired for item exchange; a PostgreSQL transaction test covers requested and offered item movement, price and reward wallet legs, and concurrent duplicate acceptance.
2. Item exchange create/accept/delete/expiry with inventory and wallet journaling, failure and retry coverage. Deletion and outstanding expiry return escrow transactionally; the creation and expiry notification outbox events have focused PostgreSQL coverage.
3. Corporation issuance, item selection, availability checks, and contract-limit enforcement are built. Public/region `SearchContracts` remains open.
4. Auction bid placement, outbid refunds, and buyout are built and covered by Host persistence tests. Durable expiry settles a winning bid and item transfer transactionally and returns the public deposit; an item-exchange expiry regression covers return/replay. Deleting an auction refunds active bids and cancels the expiry job. `GetMyBids` now returns outstanding contracts from persisted non-refunded personal or corporation bids, with contract and escrow item rows; corporate reads require the Contract Manager role. Owner paging is implemented by `GetContractListForOwner`; public/region search and the two-character headless walk remain open.
5. Courier acceptance, pickup, destination completion, and failure are wired with collateral and package settlement; a PostgreSQL test covers failure and successful destination delivery. Outstanding courier listings expire through the durable contract expiry job, which returns package escrow and removes the Plastic Wrap marker. Courier terminal notifications are written transactionally and dispatched after commit; notification ordering is covered with expiry event ordering in Host tests.
6. `tools/headless-client/tests/test_walk_contracts.py` creates a public item exchange as one character and accepts it as another, then checks the returned row, notification, escrow item ownership, issuer ownership of the unoffered stack remainder, and wallet effects. Run 57 showed the prior test assertion used the source item ID after a partial-stack split; the test now checks the escrow item ID. It is selectable in the dispatchable `live-slow` workflow; a successful rerun and restart-read comparison remain open.

A slice is complete only when its wire values, persisted state, side effects, notification order, retry behavior, and focused tests are recorded in TODO and the compatibility ledger. The graphical V24 client is a separate verification target.
## Persisted terms migration

Migration `0002_contract_terms` extends the PostgreSQL header with availability, price, collateral, creation fee, deposit, sales tax, title, and description. Migration `0003_contract_requested_items` stores requested item type and quantity terms. Migration `0004_contract_settlement_terms` records the issuer wallet account key and hangar flag for payment and requested-item delivery. Migration `0005_contract_reward_term` separates the displayed reward from outstanding escrow. Migration `0006_contract_bid_escrow` records bidder corporation context, wallet account key, and refund state. Migration `0007_courier_state` stores the Plastic Wrap item id, acceptor corporation and wallet context, collateral escrow, and completion time. Monetary columns are nonnegative with two-decimal precision, and availability is constrained to the four client modes (private, public, corporation, alliance). Existing rows receive zero-valued terms and remain readable. The schema supports creation and settlement writes; it does not itself create contracts or move inventory or ISK.


## Advanced Contracting capacity rule

The creation path uses the client `NUM_CONTRACTS_BY_ADVSKILL` values directly alongside `NUM_CONTRACTS_BY_SKILL`; the personal limit is their table sum for the current skill levels. It does not use a `+4 per level` formula. The Host checks the resulting capacity under a transaction-scoped advisory lock. The table source is V24.01 `eve/common/script/util/contractscommon.py`.
