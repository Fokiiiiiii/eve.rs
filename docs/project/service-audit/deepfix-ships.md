# Deep correctness audit: ships, fitting, modules and drones

## Scope and current status

This handoff records one high-frequency flow: launch one drone from the active ship's drone bay and follow the client updates. The current pass found no confirmed defect in this flow and made no code change. The focused fixture contains a single-item stack, so it does not verify splitting a stack of multiple drones. Fitting and module activation, multi-drone stack launch, drone return/scoop edge cases, disconnect recovery, and graphical-client behavior still need separate audits; this note does not mark the wider area complete.

## Client contract: launch drones

- The drone window launches selected bay entries through `DroneView.LaunchOrPullDrones`, which passes each `invItem` to `MenuSvc.LaunchDrones` (`/home/user/eve-logic/eve/client/script/ui/inflight/drone.py:683-695`; caller at `drone.py:691`). The group context menu uses the same menu service (`drone.py:1446-1449`).
- `MenuSvc.LaunchDrones` sends drone settings and delegates to `eveMisc.LaunchFromShip` (`eve/client/script/ui/services/menusvc.py:3430-3433`). That function serializes each item as `(itemID, quantity)`, calls the bound ship's `LaunchDrones`, interprets a dictionary whose values contain either launched IDs or error tuples, then emits `OnItemLaunch(newIDs)` (`eve/client/script/util/eveMisc.py:13-60`). The client therefore derives the old-stack to new-drone mapping from the RPC result; the Host must not synthesize a second `OnItemLaunch`.
- Both `DroneView.OnItemLaunch` and `_DroneGroupsController.OnItemLaunch` add each newly created ID to its old drone group (`drone.py:434-448`; `eve/client/script/ui/inflight/drones/droneGroupsController.py:10-37`). The drone window also refreshes when its bay item moves (`drone.py:477-484`).
- A `OnGodmaPrimeItem` is consumed by `Godma.OnGodmaPrimeItem`, which updates state and scatters a client-side `OnItemChange` (`eve/client/script/environment/godma.py:385-408`). Subsequent server `OnItemChange` notifications reach Godma's inventory state and the drone window (`godma.py:1208-1269`; `drone.py:477-484`).
- The UI handles per-item refusals through the response dictionary. `eveMisc.LaunchFromShip` raises each returned error tuple as a client `UserError` (`eveMisc.py:37-60`); the Host refusal tuple is `("CustomNotify", {"notify": text})` (`dotnet/src/Eve.Services.Space/SpaceDrones.cs:130-130, 157-254`).

## Host, state and EveJS comparison

- Host registers the bound `ship.LaunchDrones` method in `dotnet/src/Eve.Services.Space/ShipService.cs:213-229`. It parses item/quantity pairs and delegates to `ISpaceDrones.LaunchAsync`; the service returns a dictionary keyed by requested item ID with launched IDs and refusal tuples (`SpaceDrones.cs:157-254`).
- `LaunchAsync` checks the active ship/session, drone-bay ownership and location, the SDE drone category, the character's active-drone limit and ship bandwidth. It asks `CharacterShips.LaunchDroneAsync` to move one drone; a stack is split into a singleton in space, while a single drone item is moved (`dotnet/src/Eve.Services.Space/SpaceDrones.cs:157-254`; `dotnet/src/Eve.Ships/CharacterShips.Drones.cs:34-68`). Effective ship dogma is applied before the drone is sent to the simulation.
- After a successful simulation spawn, Host sends the launch item changes after the simulation's launch settle interval (`SpaceDrones.cs:246-287`; `DroneHostTests.cs:123-155`). The focused test checks the response mapping, authoritative item location/flag/singleton state, simulation launch parameters, and notification-name order for a single-item stack. It passed on database `eve_p6`: `A_drone_leaves_the_bay_the_simulation_is_asked_for_it_and_the_client_is_told` (1 passed, 0 skipped).
- EveJS 261028.1 follows the same client response shape in `/home/user/evejs-261028.1/src/server/src/services/ship/shipService.js:1345-1360`. Its runtime moves one unit from the bay, splits stacks, spawns the drone, queues `OnDroneStateChange`, primes dogma, and schedules a later inventory-row settle in `server/src/services/drone/droneRuntime.js:4842-5149, 1621-1696, 1710-1811`. The eve.rs Host test observes prime first, followed by two item changes; this is the intended two-stage inventory update, not evidence by itself of a duplicate-notification defect.
- EVE University describes the ship drone bay as capacity-limited, launch as subject to ship bandwidth and the pilot's Drones skill limit, and the return/scoop range as 2,500 m: https://wiki.eveuniversity.org/Drones. The audited launch path derives limits and item/type data from its loaded dogma/SDE state; no captured values are substituted here.

## Decision and remaining checks

The client and server agree on the request pair shape, dictionary response, per-item refusal mechanism, and client-owned stack-to-new-ID notification. The Host persists the bay-to-space item transition before returning success and emits the launch item updates after the simulation response. The focused database-backed Host test passed. No defect was established in this flow, so no code assertion was changed or weakened.

The wider task remains open: audit station fitting/unfitting and online/activation flows against all client callers and EveJS; verify multiple-drone stack splits and quantity greater than one; audit return-to-bay, abandoned-drone scoop/reconnect, bay-capacity reservations, and restart behavior; run the related test classes for any resulting fixes; verify on Actions after each push. This pass did not exercise the graphical client or inspect every consumer of inventory notifications outside the drone UI and Godma paths above.
