# EveJS 261108.1 ESS release-note port

Status: implementation and database-backed Host checks completed for automatic Main Bank registration and the autopayment countdown wire fields. The ESS entry beacon and gate transition remain incomplete, and the graphical client has not been checked.

## Verified contract

CCP's 18.11 notes describe the ESS as part of claimable null security space, with the site behind a ship-restricted acceleration gate. CCP's [Dynamic Frontiers update](https://www.eveonline.com/news/view/dynamic-frontiers-update) says each sovereign nullsec system receives a permanent ESS, except NPC-held systems. The V24.01 client consumes `mainBankLink` as a mapping (`/home/user/eve-logic/eve/client/script/ui/shared/infoPanels/essUI/controller.py:60-85,110-115`); the dynamic-resource service tests its truthiness before reading the link keys (`/home/user/eve-logic/eve/client/script/ui/shared/dynamicResource/dynamicResourceSvc.py:253-260`). An empty mapping is therefore the idle shape. The info panel reads `nextScheduledAutopayment` and `lastAutopayment` as FILETIME values for its countdown and progress gauge (`/home/user/eve-logic/eve/client/script/ui/shared/infoPanels/essUI/infoPanelESS.py:319-344,459-463`). Its ESS warp button warps to `beaconID`, while `essID` is used to determine whether the ship is inside (`/home/user/eve-logic/eve/client/script/ui/shared/dynamicResource/warpToEssStatefulButtonController.py:36-68`). Gate activation calls `keeper.ActivateAccelerationGate` (`/home/user/eve-logic/eve/client/script/ui/services/menusvc.py:3033-3040`, `/home/user/eve-logic/eve/client/script/ui/services/menuSvcExtras/movementFunctions.py:542-553`).

The new EveJS source uses claimable-system predicates covering known-space IDs, Zarzakh, the non-claimable regions, faction markers, and non-positive security (`/home/user/evejs-261108.1/server/src/services/sovereignty/sovSystemRules.js:7-16,38-73`). It emits an empty dict when a main-bank link is absent and derives the countdown FILETIMEs from the persisted payout deadline (`/home/user/evejs-261108.1/server/src/services/dynamic/dynamicResourceState.js:282-318`). Its ESS scene setup creates a distinct entry beacon and acceleration gate in addition to the bank (`/home/user/evejs-261108.1/server/src/space/encounterSurveillanceSystem.js:13-37,126-150,171-221`). That source itself says the pinned client export has no room coordinates and labels its ESS layout values as local placement policy (`/home/user/evejs-261108.1/server/src/space/encounterSurveillanceSystem.js:25-37`).

CCP's [18.11 patch notes](https://www.eveonline.com/ru/news/view/patch-notes-for-version-18-11) and the client callsites establish that the gate is part of the intended flow. They do not provide an authoritative position for a generated public entry site.

## Already present

- PostgreSQL owns ESS bank values, link and reserve state, histories, and the next payout deadline. The Host already registered the `essMgr` service and its RPC/notification callbacks in `dotnet/src/Eve.Host/Composition/EssComposition.cs:34-42,166-194`; the bank mutation and payout logic lives in `dotnet/src/Eve.Services.Space/Ess/PgEssStore.cs`.
- The client payload already carried bank identity, balances, reserve state, and main-link fields. Host wire persistence and notifications are exercised by `dotnet/tests/Eve.Host.Tests/EssMainBankHostPersistenceTests.cs:15-25,90-133`.
- The 10-second durable scheduler already runs `TickEssAsync` (`dotnet/src/Eve.Host/Composition/SpaceComposition.cs:538-539`). For systems with tick events, the Host sends per-link theft/disconnect notifications, then broadcasts `OnSystemESSDataChanged` with current store state (`dotnet/src/Eve.Host/Composition/EssComposition.cs:255-289`); the added countdown fields therefore travel on the existing state-change notification.
- The reserve-bank quadrant mapping, key consumption, bounty shares, and durable clock remain in their existing shared owners; this change did not introduce a second ESS state store.

## Ported

- Host startup now reads the pinned SDE and registers an ESS Main Bank for each claimable known-space nullsec system. Eligibility follows EveJS's predicate: system IDs 30,000,000–30,999,999, excluding Zarzakh and regions 10000070, 10000004, 10000017, and 10000019, with security at most zero and no faction marker. Representative pinned SDE source rows are `.cache/sde/eve-online-static-data-3396210-jsonl/mapSolarSystems.jsonl:21,142,208,326,5432`; the Host integration test verifies the full 3,285-system selected count. IDs use the existing EveJS generated-item base, plus the system ID. The implementation is in `dotnet/src/Eve.Host/Composition/EssComposition.cs:21-25,44-89`; the bulk insert preserves bank contents and deadlines on conflict in `dotnet/src/Eve.Services.Space/Ess/PgEssStore.cs:147-169`.
- The Host sends each ESS ball to the simulator when that solar system enters through `SpaceSessions.SystemEntered` (`dotnet/src/Eve.Host/Composition/SpaceComposition.cs:620-628`, raised after a pilot enters in `dotnet/src/Eve.Services.Space/SpaceSessions.Ships.cs:129`). It reads only that system's persisted bank identity with `PgEssStore.PlacementAsync` and uses the cached SDE anchor reader (`dotnet/src/Eve.Host/Composition/EssComposition.cs:217-254`, `dotnet/src/Eve.Services.Space/Ess/PgEssStore.cs:211-234`, `dotnet/src/Eve.Services.Space/Sites/SiteAnchors.cs:18-46`). A real Host + Rust simulator test checks that no ESS is placed for an unentered system and that the entered nullsec system receives its bank ball.
- Host projects the persisted next payout deadline and preceding interval start to client FILETIME values (`dotnet/src/Eve.Services.Space/Ess/PgEssStore.cs:650-673`). `essMgr` now includes both countdown fields and serializes an idle `mainBankLink` as an empty `PyDict` (`dotnet/src/Eve.Services.Space/EssMgrService.cs:187-217`).
- `dotnet/tests/Eve.Host.Tests/EssSystemDeploymentCompositionTests.cs:95-155` exercises real Host registration against SDE 3396210, verifies the full 3,285-system eligibility count and representative NPC-nullsec, Pochven, and highsec exclusions, checks wire fields, and confirms that restart preserves generated IDs and payout deadlines. `dotnet/tests/Eve.Services.Space.Tests/PgEssStoreTests.cs:356-375` checks payout boundary behavior and the countdown projection. Host RPC persistence, state changes, and notification order remain covered in `EssMainBankHostPersistenceTests`.

## Rejected or still open

- EveJS generates an ESS entry beacon, gate, decloak clouds, and a pocket/deadspace transition. The V24.01 client callsites confirm that a separate `beaconID` is used for warp and that an acceleration-gate RPC exists, but this repo has no ESS-specific public-gate registration and admission flow. The current Host still uses the Main Bank ID as `beaconID` (`EssMgrService.cs:200-203`), and Host placement creates only the bank ball (`dotnet/src/Eve.Host/Composition/EssComposition.cs:217-252`).
- The EveJS generated positions and deadspace geometry were not copied. EveJS calls the layout values local placement policy and notes that the client export lacks the needed room coordinates (`/home/user/evejs-261108.1/server/src/space/encounterSurveillanceSystem.js:25-37`); neither that geometry nor a generated public-gate arrival point is independently supported by the pinned client or an authoritative TQ source checked for this port. Do not read the auto-registration/countdown work as full ESS deployment parity.
- No graphical V24.01 client walk or direct TQ comparison was performed. Automatic site visibility, warp target availability, gate admission, and the in-space transition therefore remain unverified here.

Moving placement to `SpaceSessions.SystemEntered` removes this startup work. Run 1685 passed the required CI gate with no failed jobs after that change ([run 1685](https://github.com/Fokiiiiiii/eve.rs/actions/runs/42819120863)).
