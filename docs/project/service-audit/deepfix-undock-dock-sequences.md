## Defects fixed

1. The generic `CmdDock` path previously treated any non-station ID as an ordinary simulator dock, bypassing structure ACL. It now routes known structures through the same Host access check; the V24 client uses the dedicated structure RPC (`SpaceSessions.Movement.cs:20-56`, `SpaceSessions.Structures.cs:10-65`, `StructureComposition.cs:336-339`). A registered-Host regression covers denied and allowed generic calls (`StructureDockingTests.cs:68-87`).
2. The simulator previously finalized and removed the pilot after four seconds, before Host could recheck mutable timers or ACL. It now emits readiness command 255, keeps the pilot pending, and accepts Host's station-scoped decision command 254; denial clears pending docking and restores ball mass, while approval alone emits `Docked` (`crates/eve-space/src/scene/mod.rs:110-111,128,230`, `scene/session.rs:542-543,775-787`, `scene/docking.rs:198-252`, `sim/dispatch.rs:14,168-169`). The Host readiness match is excluded from the earlier generic `SimAccepted` handler so it reaches final authorization (`dotnet/src/Eve.Services.Space/SpaceSessions.cs:949,972-976`); final checks use current module restrictions, movement/Crimewatch policy and structure ACL (`SpaceSessions.Movement.cs:550-581`). Pilot teardown now also occurs after a decision command reports `Docked` (`crates/eve-space/src/sim/spawn.rs:816-820`, `sim/dispatch.rs:168-169`).
3. When the delayed final check denied docking, the client had received `OnDockingAccepted` but no terminal notification; its tactical docking state could therefore remain set. EveJS also only clears pending state and logs the delayed failure (`tick.js:2403-2411`), but the complete V24 consumer trace shows `OnDockingFinished` is the only event that clears that state. Host now sends that terminal event on a denied final decision while leaving the pilot and session in space (`SpaceSessions.Movement.cs:575-581`). It does not send a location/session transition. Registered-Host tests cover revoked structure access and a weapons timer that starts during the delay (`StructureDockingTests.cs:91-123`, `SpaceServiceTests.cs:2141-2155`).
4. If the persisted active ship was absent from the station hangar, Host previously returned `None` after either a missing ship snapshot or a refused `CharacterShips.UndockAsync`, although the V24 station client uses `ShipNotInHangar` for this recovery path. Host now throws that user error in both cases, without fabricating a capsule ID (`SpaceSessions.Ships.cs:66-68,157-160`). EveJS suppresses the generic failed-undock result as `null`; the difference follows the explicit client handler at `base.py:499-504`. The new PostgreSQL Host regression moves the active ship out of the station hangar and checks the error, unchanged session/item location, and no simulator entry (`SpaceServiceTests.cs:1185-1205`). It failed before the fix because no exception was thrown.

## Successful completion order

After simulator approval, Host persists the ship and condition through `Ships.DockAsync`, removes the pilot, sends `OnInvulnCancelled`, releases bound objects, sends `OnItemsChanged`, applies the station or structure session tuple, then sends `OnDockingFinished` and invokes `DockedLocationChanged` (`SpaceSessions.Movement.cs:599-650`). Station and structure tests assert the wire notification/session ordering; no successful-path order was changed. Station docking sets `stationid/locationid` and clears `solarsystemid`; structure docking sets `structureid/locationid/solarsystemid` and clears `stationid`, matching GameUI's view transition consumers above.

### Undock completion order

Host commits `CharacterShips.UndockAsync` before entering the simulator; a simulator refusal calls `RecoverFromSpaceAsync` and returns the client-visible availability error. On success it registers the pilot, sends `OnItemsChanged`, clears server `stationid2`, changes `shipid` and the station/structure plus location/system session values, then sends `OnInvulunOnUndockingUpdated` (`SpaceSessions.Ships.cs:91-152`). EveJS likewise emits the item change, attaches the ship to the space scene, flushes the session change, then sends the undock invulnerability notification (`transitions.js:2378-2386,2430-2468`). The client uses the resulting session fields to select the station/structure/space view (`gameui.py:565-641`) and consumes both undock invulnerability events in the five listeners listed below. The station client does not assign the return value from `PerformSessionChange` (`station/base.py:491-521`); EveJS records the bound-object response shape and says the client does not consume it (`shipService.js:2135-2141`). Host returns its bound-object and session cooldown values after the transition (`SpaceSessions.Ships.cs:164-165`).

## Additional whole-client checks (2026-11-03)

- The NPC station path is `MenuSvc.DockStation -> GetCloseAndTryCommand -> AutoPilot.NavigateSystemTo -> RealDock -> PerformSessionChange('dock', bp.CmdDock, stationID, shipID)` (`menusvc.py:113,2989-2995,3698-3700`; `autopilot.py:502-530,549-553`; `movementFunctions.py:503-518`; `sessions.py:418-500`). The 2,500 m value is the client's command trigger distance. Outside the 500 m surface range, the simulator starts `FollowBall`, reports `Approaching`, and keeps steering toward the station; Host returns `DockingApproach` with the rounded distance. The ship is not docked on arrival: the client must issue another dock request once in range, as the EveJS path does (`scene/docking.rs:185-190,257-265`; `SpaceSessions.Movement.cs:49-59`). No client code special-cases the literal `DockingApproach`; the client autopilot propagates the user error after cancelling its own navigation. The simulator's follow command continues independently.
- Structure docking is separate: the client navigates to 2,500 m and calls the structure RPC, handles `DockingRequestDenied`, and refreshes structure state for ordinary denial while suppressing refresh for `ShipTooLarge` (`structureDocking.py:64-81`; directory/overview/bracket consumers at `structureDirectory.py:132-137`, `overviewWindow.py:555-557`, `bracketMgr.py:888-891`). Station undock catches `ShipNotInHangar` and prompts on `ShipContrabandWarningUndock` (`station/base.py:488-521`).
- Structure undock uses its own RPC inside `PerformSessionChange`; it handles only `ShipContrabandWarningUndock` and rethrows other `UserError`s (`structureDocking.py:25-52`). Host routes that RPC to the same `UndockFromAsync` used for station undock (`SpaceSessions.Structures.cs:84-92`), so `ShipNotInHangar` reaches station recovery and propagates as a user error through structure undock.
- Whole-client searches found exactly three `OnDockingAccepted` consumers: `dockingHeroNotificationService.py:33-35`, `spaceMgr.py:510-518`, and `tacticalNavigationService.py:486-489`. `OnDockingFinished` has two consumers: `dockingHeroNotificationService.py:114-118` and `tacticalNavigationService.py:491-495`; there is no `OnDockingAborted` consumer. The two undock invulnerability notifications each have five consumers: `crimewatchTimers.py:483-485,493-496`, `baseActivationController.py:136-146`, `pvpFilamentController.py:250-258`, `randomJumpController.py:180-188`, and `void_space_activation_controller.py:189-197`.
- A whole-client search found no `session.stationid2` attribute consumer. The `stationid1/stationid2` names in `eveServiceCallGPCS.py:16-24` are the old/new station values used to check whether the session still routes to the same station. Host clears its server-side `stationid2` value on undock (`SpaceSessions.Ships.cs:144-145`); no separate client session change for this server field is required.
- Test setups that isolate docking behavior account for the session cooldown after `InSpaceAsync`: the mission-hook test ends it explicitly (`SpaceServiceTests.cs:1042-1050`), the module test waits for timer expiry (`2125-2132`), and the weapons-timer test ends it before starting the delayed dock (`2141-2148`). Without this, `DockAsync` exercised session cooldown first. The mission-hook case passed alone; after merging main, all four related Host test classes passed.
