# Feature gate

`tools/dev/feature-gate <area>` reports whether a configured service or RPC family has evidence for the six completion checks. It exits `0` only when all six pass; a missing source, test report, or explicit review is a failure. By default it writes the JSON report to stdout and the short summary to stderr. `--report path.json` writes the JSON file and prints the summary to stderr.

The command uses only Python's standard library plus the repository's existing Rust, .NET, PostgreSQL, and live-test tools. It uses the same V24 client inventory and active Host registration scan as `tools/spec-extract/generate_service_audit.py`. For formatting, clippy, and selected .NET tests it runs the same commands or `tools/dev/agent-test.py` used by CI. A configured trace replay uses `tools/dev/run-eve-live.sh` and `tools/mitm/mitm replay`.

## Add an area

Add one entry to `tools/dev/feature-gate-areas.json`:

1. Give it a stable CLI name such as `ship-rpcs`.
2. Define `rpc_scope`. Use `{ "service": "ship", "all_client_methods": true }` for a whole service. For an RPC family, list the exact `service` and `methods`; take the members from the whole-tree V24 inventory and keep the list current when client callsites change. If the inventory scanner does not recognize a client bound-object accessor, add `client_callsites` references by method; the gate checks that each referenced V24 source line still contains the method name.
3. Set `host_e2e` to one test that runs through the actual Host method table and wire dispatch while using PostgreSQL state. Its source markers must show the Host call, response wire value, persisted state, and notification assertion, with a PostgreSQL fixture/harness marker. The test and every selected area project are run and their TRX results are checked; skipped tests fail.
4. Add `error_inventory.cases` mapping each reviewed V24 client-visible failure to its client file and line, test method, and asserted error. Set `complete` to `true` only after the full client call paths for this area have been reviewed against the failure cases. An explicitly partial inventory fails even when its known cases pass.
5. Add each intentional difference from the V24 client or EveJS to `deviation_review.entries`, with the exact `DEVIATIONS.md` heading and a reason marker from that section. Set `complete` to `true` only after the whole area comparison is recorded. If none are known, use `entries: []` and `none_known: true` after recording the comparison.
6. Set the test projects and `dotnet_filter`. The gate runs workspace `cargo fmt --all --check` and `cargo clippy --workspace --all-targets -- -D warnings`, then calls `tools/dev/agent-test.py` for the selected .NET projects and tests. Add Rust packages under `rust_check_packages` when the area needs `cargo check -p ...` as well.
7. Add at least one `replay_cases` entry. A `headless` case uses `{"kind":"headless","test_file":"test_area_walk.py"}`. A `trace` case uses `{"kind":"trace","fixture":"tools/headless-client/fixtures/area.jsonl.gz","connection":4,"allowlist":"tools/headless-client/fixtures/area-allowlist.json"}`. Trace allowlist entries need `owner_job` expiry hooks, and the existing replay contract fails when an allowlisted signature stops appearing. Keep those records and their behavior aligned with `docs/project/live-trace-replay.md`.

Run a configured area with a PostgreSQL database and the pinned SDE available:

```sh
EVE_PG_URL=postgres://postgres@127.0.0.1:5432/eve_p5 \
  tools/dev/feature-gate ship-rpcs --report .agent-test-logs/ship-rpcs-feature-gate.json
```

The CI runner supplies PostgreSQL and loads the pinned SDE before its tests. Locally, use the repository's PostgreSQL setup and a dedicated database such as `eve_p5`; PgFact tests skip if `EVE_PG_URL` is absent, and the gate treats any selected-test skip as failure. Trace cases also need the headless-client virtual environment and `.cache/sde`.

## Evidence limits

RPC family membership, error-case completeness, and the compatibility-difference review are maintained in the area manifest. The command reads the checked-in whole-client matrix generated by `generate_service_audit.py`, verifies selected matrix callsite lines still exist and name the method, re-scans current Host registrations, verifies every listed error test and deviation reason, and requires an explicit completeness attestation. Regenerate the matrix with the existing audit tool when the client inventory changes. The current inventory scanner misses calls obtained through `GetShipAccess()`; the ship example supplies those V24 callsite lines explicitly. The command cannot infer a reviewer's unlisted RPC-family members or prove that a hand-maintained error inventory is exhaustive. Keep the manifest's client callsites and review record current, and do not set a completeness flag without the corresponding source review.

The worked `ship-rpcs` area covers the fitting, ship recovery, maintenance-bay, drone, and password methods listed in `feature-gate-areas.json`. Its whole-client callsites are `fittingSvc.py:510`, `invItemFunctions.py:38`, `menusvc.py:3254-3331`, `menuFunctions.py:218`, `playerOwned.py:190`, and `droneFunctions.py:195`. Its Host socket tests and PostgreSQL state tests are separate, so item 2 fails until one test covers both paths with persisted state and notification assertions. It records three known failing cases but deliberately leaves the error inventory incomplete. It has no ship-specific recorded headless walk or trace yet. The gate reports these gaps as failures instead of treating the existing generic owner trace or selected refusals as completion evidence.

The comparison record documents two known differences for this area. eve.rs implements `ScoopToInfrastructureHold` because V24 invokes it from `eve/client/script/ui/services/menusvc.py:3304-3308`, while EveJS 261108.1 has neighboring scoop handlers at `server/src/services/ship/shipService.js:1376-1414` but no handler for this method. EveJS can also scoop Mobile Tractor Units, whose runtime is not implemented in eve.rs. The manifest ties both differences to reasoned entries in `docs/reference/compat/DEVIATIONS.md`; item 5 checks those entries against the comparison record.
