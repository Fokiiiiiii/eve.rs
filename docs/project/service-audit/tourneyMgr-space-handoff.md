This note records the evidence for the tournament participant, restriction and grid work. It does not certify every `tourneyMgr` client call, the graphical client, or full production deployment.

## SimLink protocol 90 metrics

Protocol 90 adds correlated tournament metrics read/reply messages 154/155. The request retains the v89 metrics identity; each reply companion adds an optional fighter member count. Absent, known zero and positive counts through 64 remain distinct; drone counts, invalid flags and out-of-range values are rejected. Existing 148–153 payloads and the v89 fixture remain unchanged. The Rust v90 simulator binary was rebuilt; that compilation alone is not a live gameplay check.

## Registered cleanup and autobanning

`CleanupGrid` now authenticates the bound referee and drains the existing durable postgame cleanup worker after committing the authorization transaction. The worker distinguishes completed, progressed and blocked outcomes; the RPC permits at most 256 steps or 15 seconds and returns an error while any target remains unconfirmed. The existing postgame job remains responsible for retry, and a completed cleanup can be called again. `AbyssalHostFlowTests.Tournament_cleanup_registered_wire_waits_for_confirmed_removal` passed 1/1 with no skips using registered encoded RPC, PostgreSQL and Rust sim: a missing removal acknowledgment produces an error, a restored live wreck is guarded and removed, replay succeeds, and an outside wreck, unrelated owner wreck and beacon remain. The completed match and postgame job were seeded in this fixture; the full match lifecycle was not exercised here.

`AbyssalHostFlowTests.Tournament_autobans_registered_wire_prompts_connected_captains` passed 1/1 with no skips using registered encoded RPC, PostgreSQL and Rust sim. It creates the match through the registered service, submits the client keyword arguments with two live participants, verifies both prompts and the deadline, and confirms a replay does not duplicate them.

## Evidence and scope

* The V24.01 client calls `TeleportPlayers(matchID, team, beaconIndex)` and `ReturnTeamPlayers(matchID, team)` in `eve-logic/eve/devtools/script/tournamentRefereeTools.py:1271-1283`. Its range-check center and radius are local to `allianceTournamentSvc.StartTracking` (:1316-1333); `CleanupGrid` sends only the match ID (:1162-1165).
* CCP's Thunderdome guide says pilots must be docked before team teleport, that a nominated fleet member need not be fleet boss, and that teams, grid and referees are returned/cleaned at 60/65/70 seconds after completion: https://cdn1.eveonline.com/community/thunderdome/Thunderdome_Tool_Guide.pdf, pp. 7-9.
* The server requires an operator-configured region rather than deriving one from the local range-check widget. The current Host input is `EVE_TOURNAMENT_REGION_IMPORT`, a JSON array of `{solarSystemId, centerBeaconOrdinal, radiusMeters}`; the beacon ordinal is zero-based. The center must resolve to a configured arena beacon, and radius must be positive and finite.
* Teleport journals preserve the original location and separate stable outbound/return operation IDs. An acknowledged docked entry must also be in the configured physical region; a collision may displace it. A retry with no successful local acknowledgment does not infer success from region proximity alone. An ambiguous result remains pending.
* Movement, warp and lock gates consult the match owner's initialized read-only projection. A failed post-commit refresh remains fail-closed and a durable recurring job reconciles it. Participant return records follow committed `space.transition` death and home-only ship-switch events; the initial roster entry is retained.
* Grid cleanup snapshots match-owned wreck candidates into the durable target journal after participant returns. A correlated simulator operation checks live wreck identity and physical region before removing it. It preserves unmatched objects and beacons. The present implementation targets wreck group 186; this is not evidence that all possible debris, drones, corpses, or deployed objects are cleaned.

The real-simulator/PostgreSQL player fixture also verifies that a public pilot in another actual solar system receives no `OnPreMatchStart`, even when its session system is spoofed so that `CharacterSessions.InSpace` includes it as a candidate. The same fixture passed 1, with 0 skipped.

The simulator entry for a docked ship currently has no durable operation-correlated receipt. If the simulator accepts `SimEnter` but its response is lost, the host can treat the result as unavailable and recover persistent state while the simulation may already contain the ship. Do not treat the DB-reset retry test as proof of this network-failure case. A correlated idempotent entry/receipt and an actual lost-response test are required.

The cleanup journal's `sim_seen` alone does not prove a guarded removal: an out-of-region target may be seen and then a process may fail before the guarded command. The current code leaves the target pending if it is absent from a loaded scene, `sim_removed` is false and its persistent item remains. The real-simulator/PostgreSQL cleanup fixture passed (1 passed, 0 skipped): it verifies that state remains pending, then restores the actual wreck, expires the lease, and verifies guarded removal and preservation of unrelated objects. It models withholding the durable ACK, not an actual network response loss. A genuinely lost remove acknowledgment can therefore remain pending until durable guarded-removal evidence or another safe authoritative reconciliation is available; `sim_seen` is never sufficient proof by itself.

Actual collision-adjusted arrival outside the configured physical region must leave the participant journal pending and must be recoverable through a real safe return. The positive collision test and outside-beacon precheck do not by themselves verify that negative arrival/recovery scenario. Full multi-process restart, actual graphical client interaction, exact CCP operator-tool end-to-end behavior, and `ReturnAllPlayers` as a separately exercised encoded call remain unverified.
