# ADR 0015: Player fighters are companion sessions on the drone machinery, with abilities as effect handlers

- Status: accepted. The fighter track is complete at protocol 32 except kamikaze and LaunchBomb, which are refused by name (third amendment).
- Date: 2026-10-08
- Decided by: the project lead, for the player fighters track. All recommendations were accepted; the decisions are the numbered items FIG-D-1 to FIG-D-11 and FIG-X-1 to FIG-X-4 below.

## Context

Fighters launch from a tube, fly as a squadron in space, and run abilities (for example Tackle, AttackM, LaunchBomb,
Propulsion). The client sends the orders; the server answers and sends notices. The drone path already does launch, move,
scoop and destroy, so a second stack would duplicate stores and the bridge (FOUNDATIONS section 5 forbids duplicate stores
and `if effect.Name` branches). The pinned SDE gives slot 0 and the ability families, but not the ability slot order, the
cooldowns or the charge counts (the client reads those from its own static resource, which the repository does not carry).

## Decision

1. **Companion sessions (FIG-D-1).** Fighters run on the drone machinery. Each ability is an Effect Registry handler.
2. **Ability facts (FIG-D-2, hybrid).** Families and slot 0 come from the SDE (`isDefault` effect). Slots 1..n, cooldowns and
   charges come from a facts file generated by a `tools/spec-extract` script into the git-ignored `out/` directory and loaded
   from a configured path. The loader cross-checks the family set against the SDE for all 94 types. Client-derived data is
   never committed. Without the file, activation returns an honest `UserError` and the tests are SKIPPED, never passed.
3. **Tackle (FIG-D-3).** A list of remotes in `Action::Remote` and `SimAction.Remote`. A single remote is a list of one.
   Decided with FIG-X-3 so there is one remote shape.
4. **Abandoned squadron (FIG-D-4).** Kept in space, as EveJS does. The drone difference (deletion) is recorded separately.
   Any stray-item cleanup reuses the scheduler sweeper pattern, not a new timer.
5. **Sim identity (FIG-D-5).** `CompanionLink{kind}` with one command carrying a kind byte. The kind defaults to drone, so the
   drone wire is unchanged.
6. **LaunchBomb (FIG-D-6).** A visible refusal with a LIMITATION entry until the `Area` mechanism (ADR 0011) exists and the bombs
   spec is written. No bomb entity is invented.
7. **Notification order (FIG-D-7).** Reply first, then the queued ability notice; tube and removal notices synchronously; all
   published after commit (FOUNDATIONS rule 2).
8. **GOTO_POINT (FIG-D-8).** An additive point variant of `Course` (the shared enum also serves drones and ships).
9. **Scoop into cargo or fleet hangar (FIG-D-9).** EveJS refusal, as a `UserError` (not silent). No CCP source for it is recorded.
10. **No fighter provider installed (FIG-D-10).** `UserError` per id or per call, through `MachoErrors.UserErrorPayload` so the
    client reads `error.args`. Never `None`, `False` or an empty result as success.
11. **Restart (FIG-D-11).** Squadrons in space are not rebuilt on restart. The item row stays and is recovered on logon, as drones
    are. Recorded as a LIMITATION.
12. **Protocol (FIG-X-1).** One protocol epoch; one bump by the integrator after the wire batch (ADR 0013 rule 7).
13. **Link kinds (FIG-X-2).** Companion kinds are generalised (FIG-D-5). `link.rs` holds a kind-range table naming each owner.
14. **Remote shape (FIG-X-3).** The shared shape is a list of remotes in `Action::Remote` / `SimAction.Remote`. `Area` (ADR 0011)
    applies the same list per target.
15. **File collisions (FIG-X-4).** One owner per file per batch; batches are serial where a file is shared.

## Consequences

* Drone refactor (`CompanionBridge` extracted from `SpaceDrones.OnReceived`) must keep `drone_flight.json` and the drone tests green.
* Abilities beyond slot 0 stay refused until the owner supplies the facts file. The file needs a client install to generate, so
  it cannot be produced by the repository alone. This is a LIMITATION, not a success path.
* Work cycles for fighters are not part of `CompanionBridge`; the mining work cycle (ADR 0013) keeps them.
* Open items (CCP scoop rules, AttackM damage model, event names from the client, abandoned-squadron cleanup,
  destruction item removal, the capacitor check on a companion pilot) are recorded in DEVIATIONS "Player fighters" where a row names them; none is claimed as checked in the graphical client.

## Amendment (2026-10-09): ability facts from EVE.js and the SDE

The owner's directive for this track replaces FIG-D-2 for the ability facts. The facts file is not generated from a client install. The slot order, cooldowns and charges come from the EVE.js extraction (`tools/DatabaseCreator/staticTables/fighterAbilities/data.json`, generated from the client static cache), committed as `dotnet/src/Eve.Services.Space/Effects/Data/fighter-abilities.json` (an embedded resource, read by `FighterAbilityCatalogue`). The families and the counts per family agree with the pinned SDE for all 94 types (`FighterAbilityCatalogueTests`). The file is a derived copy with its provenance in its `source` block; it is regenerated from EVE.js, never edited by hand. The SDE effect name of the AttackM family is `fighterAbilityAttackM`; EVE.js calls the family `fighterAbilityAttackMissile`.

The wire protocol is not changed by this batch (main is at protocol 30 with the tractor beam; the fighter kinds take 31 with WP-E). The provider interface is `ISpaceFighters` in `Eve.Services.Core` (the service routes to it) and its implementation is `SpaceFighters` in `Eve.Services.Space`, which serves the database side of the fighter calls.

## Amendment (2026-10-09, second): the squadron out in space

- **Companion kind (FIG-D-5).** `DroneLink` carries `kind: CompanionKind` (`Drone` by default, `Fighter` for a squadron) instead of a generalised `CompanionLink`. The drone wire and drone behaviour are unchanged: drone orders refuse a squadron (`NOT_CONTROLLED`), and a squadron's controller gets no drone-state notices. The ball of a squadron is `Kind::Fighter`.
- **Wire (FIG-X-1, FIG-D-5).** Fighter messages take kinds 54-58 (`LaunchFighter`, `FighterOrder`, `FighterResults`, `FighterLanded`, `FighterReleased`) and protocol 31. The drone command was not generalised with a kind byte, so the drone codec and its fixtures stay as they are. `messages.json` is regenerated by `tools/dev/gen-simlink-fixtures.py` on both sides.
- **Orders (FIG-D-8, partly).** Orbit, follow, stop, recall and abandon are served. `GOTO_POINT` is refused with its reason: `Course` has no point variant (the additive variant that D-8 asks for is not in yet).
- **Landing and release.** A recalled squadron lands when it is within `FIGHTER_RECOVERY_DISTANCE` (5,000 m) of its ship: the simulation says so (`FighterLanded`) and the host moves the item into its tube, sending the reference's notices. An abandoned squadron stays in space (FIG-D-4) and the host is told where (`FighterReleased`).
- **Not in this batch, each refused with its reason:** ability activation and deactivation (the remote list of FIG-D-3 and the Effect Registry handlers), squadron damage and death (WP-I), scooping an abandoned squadron back (FIG-D-9, WP-R), recovery on logoff or ship loss (WP-R), LaunchBomb (FIG-D-6, ADR 0011), the recorded EVE.js oracle (WP-S) and restart (FIG-D-11, a LIMITATION).

## Amendment (2026-10-09, third): the batch that completes the fighters

The items that the second amendment refused are now served, except where a named blocker remains:

- **Abilities (FIG-D-3, WP-K, WP-L, WP-M).** A slot's ability is a simulation effect built from the squadron type's own dogma (`Effects/FighterAbilityEffects.cs`). The projected families (warp disruption, stasis, neutralizer, ECM) and the tackle go through `ProjectedEffect`. Tackle is one remote, `Remote::Tackle` / `SimRemote.Tackle` (wire tag 12): a warp scramble and a web on the same target, which is the list of FIG-D-3 in its only form that is needed (one remote per effect, so one module runs it; no second shape). The self buffs (microwarpdrive, afterburner, evasive maneuvers) are plain percentages of the squadron's numbers; the micro jump drive uses its slot's cooldown. Missiles and AttackM land per member on the locked target.
- **Squadron health and death (WP-I).** The squadron's health is the points of all its members together; `tell_squadron_size` tells the size when a member is lost (a size only falls). The last member's loss destroys the squadron, and the host removes its item. The launch message carries the size (`LaunchFighter.squadron_size`).
- **Scoop and logoff recovery (WP-R).** A squadron let go is scooped back into the bay or a tube within 5000 m of the ship it came from (`FighterOrder` code 7). The simulation checks the distance and the launching ship; the database checks the room and the tube rules, and a refusal puts the item back in space. A pilot who logs off lands the squadrons within 5000 m of its ship (`release_drones` with the logoff place) and lets go the rest.
- **GOTO_POINT (FIG-D-8, WP-H).** `Course::GotoPoint` is a point course, and `FighterGotoPoint` (kind 59) carries the point. Protocol 32 is the one bump for this batch.
- **Still refused, with the blocker named.** Kamikaze: the simulation has no approach-and-detonate action. LaunchBomb: the general `Area` of ADR 0011 is not built, and the bomb's detonation delay and trajectory need a captured V24.01 trace (the ADR 0011 addendum). Both are refused with their reason, never run as a no-op.
- **Oracle (WP-S).** No live client runs on this host, so no recording was made. The fighter wire shapes are pinned by `oracle/fixtures/simlink/messages.json`, written from the EVE.js and eve-logic source (see DEVIATIONS, Player fighters).
- **Limits kept as LIMITATIONs** (DEVIATIONS): charges and cooldowns are in memory; an abandoned squadron's size is not written back after its release; restart does not rebuild squadrons in space (FIG-D-11).
