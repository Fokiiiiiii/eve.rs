# Corporation, contract, and Crimewatch audit fixes

Audit source: external findings H-03, H-07, M-02, and M-03. The findings were checked against the whole V24.01 client checkout at `/home/user/eve-logic`, EveJS v0.12.9 at `/home/user/evejs-261108.1`, the local Host routes and stores, and PostgreSQL-backed Host tests.

## H-03 — Alliance contact label IDs are masks (confirmed)

The client uses a returned `labelID` directly as a bit mask. `/home/user/eve-logic/eve/client/script/ui/shared/neocom/addressBook/addressbookService.py:1015-1020` caches and returns the RPC result unchanged; `:1022-1039` routes personal, corporation, and alliance contact books; `:1096-1114` passes that value to `AssignLabels` and ORs it into the cached mask; `:1133-1146` passes it directly to `RemoveLabels`. The corporation and alliance proxies forward the mask unchanged (`/home/user/eve-logic/eve/client/script/ui/services/corporation/base_corporation.py:1025-1030`; `/home/user/eve-logic/eve/client/script/ui/services/alliances/all_cso.py:275-280`). A whole-script search found no other contact-label RPC caller that changes its meaning. EveJS allocates one-hot IDs and applies those IDs with bitwise OR/AND-not (`/home/user/evejs-261108.1/server/src/services/corporation/contactLabelState.js:56-94`; corporation and alliance RPC handlers in `corpRegistryRuntime.js:813-898, 2086-2173`).

The old alliance store returned sequential IDs `1, 2, 3`, while interpreting them as bit positions. The third label therefore collided with the first two bits on the wire. Alliance labels now allocate and persist one-hot masks (`1, 2, 4, ...`), accept only one-hot mask inputs, and use the returned mask directly for assignment, removal, and deletion. Migration `020_alliance_contact_label_masks` converts legacy sequential IDs while preserving existing contact masks. Corporation labels already allocate one-hot IDs in `dotnet/src/Eve.Corporations/CorporationStore.Alliance.cs:1004-1027`; personal labels do so in `dotnet/src/Eve.Services.CharacterInfo/CharMgrService.cs:747-782`. They do not share the broken alliance allocation code, so their wire behavior was left intact.

The registered alliance Host test creates three labels, assigns/removes/deletes the third using the exact returned mask, verifies notification and persisted state, and checks migration of legacy IDs. Against the pre-fix code, that Host test failed because it returned `[1, 2, 3]` instead of `[1, 2, 4]`. The EveJS `contactLabelState.allocateNextLabelID` helper was run directly and returned `1, 2, 4`; its RPC routes were source-traced. Local graphical-client behavior was not exercised.

## H-07 — Role stasis does not block voluntary departure (false positive)

The finding treats forced removal and voluntary departure as one rule. V24 distinguishes them: `/home/user/eve-logic/eve/client/script/ui/shared/neocom/corporation/corp_ui_home.py:530-548` calls `CanLeaveCurrentCorporation`, offers `RemoveAllRoles` when active roles block departure, and calls `KickOut(session.charid)` for a permitted self-departure; `/home/user/eve-logic/eve/client/script/ui/services/corporation/base_corporation.py:394-412` routes self-removal through `CanLeaveCurrentCorporation` and removal of another member through `CanBeKickedOut`. Invitation acceptance is a separate client action (`/home/user/eve-logic/eve/client/script/ui/shared/neocom/corporation/corp_ui_applications.py:757-759`). The UI does not automatically remove roles. CCP's published rule allows a member to leave immediately after dropping roles, but requires the role-removal wait before a forced kick ([Team True Grit Brings Some Changes This May](https://www.eveonline.com/news/view/team-true-grit-brings-some-changes-this-may), 2013-05-14). EveJS makes the same distinction: `Handle_CanLeaveCurrentCorporation` checks the member's roles, while `Handle_CanBeKickedOut` checks stasis (`/home/user/evejs-261108.1/server/src/services/corporation/corpRegistryRuntime.js:3851-3884`); self and other-member paths branch separately at `:3886-3916`. Invitation acceptance invokes the voluntary departure rule at `:2479-2503`.

eve.rs follows that behavior. `CorporationStore.Membership.cs:210-220` checks membership, roles, and CEO status for voluntary leave; `:222-233` uses it for leave; `:194-201` uses it before invitation acceptance. The forced-kick path adds the stasis check at `:235-248`. A PostgreSQL-backed Host test registers the real `corpRegistry` and verifies that a stasis member cannot be force-kicked, can voluntarily leave, and can accept a move invitation after dropping roles. This Host test passed against the pre-fix code, consistent with the finding being a false positive. No production change was justified. A test asserting that stasis blocks voluntary departure would contradict the verified client and CCP behavior, so it was not retained as a regression assertion.

## M-02 — Empty item-exchange offers are client-valid when paid for (confirmed)

The client requires offered items for auctions and courier contracts (`/home/user/eve-logic/eve/client/script/ui/shared/neocom/contracts/createContractWnd.py:1358-1373`), but does not apply that requirement to item exchanges. Its item-exchange checks at `:1455-1470` reject simultaneous positive price and reward, require a public minimum price when no requested items are supplied, and reject a one-sided public contract only when it has no offered items and no positive reward. Thus an assigned/private item exchange with no offered or requested items and a positive reward is allowed. EveJS likewise requires items only for courier and auction contracts (`/home/user/evejs-261108.1/server/src/services/contracts/contractRuntimeState.js:1111-1147`).

`ContractCreationRules` now applies the non-empty-item requirement only to auction and courier types while retaining the 500-item limit and item validation. Against the pre-fix code, the real Host RPC test for a private item exchange with no items and a positive reward failed because it received an error response (Macho state 15) instead of `CallRsp` (state 7). It now verifies successful creation, reward escrow, fees, expiry scheduling, notifications, and persisted contract state. The EveJS create validator was source-traced; an end-to-end EveJS contract creation was not run because the isolated contract world fixture was unavailable.

## M-03 — Lost module-end events left combat activity indefinite (confirmed)

The client consumes Crimewatch state notifications and projects finite and active timer states (`/home/user/eve-logic/eve/client/script/ui/services/crimewatchSvc.py:222-232`; `/home/user/eve-logic/eve/client/script/ui/crimewatch/crimewatchTimers.py:360-392`). EveJS ties module combat activity to the simulation effect lifecycle: each scene tick checks whether active module effects remain, and removes activities when the effect or scene ends (`/home/user/evejs-261108.1/server/src/services/security/crimewatchState.js:3925-3980, 5066-5074`). eve.rs previously removed activities only after the explicit end callback.

eve.rs timestamps each accepted module-aggression update. The simulation now sends internal simlink kind 162 every 30 seconds while an offensive module effect is still running, including while a module waits for a Host response; the Host refreshes only an existing activity record. Crimewatch expires activity after 60 seconds without a heartbeat or new aggression update. On an expiry or explicit end, it commits finite timer state before removing the activity from the active set; a concurrent `GetClientStates` sees either the active timer or the new finite expiry, not an older persisted deadline. Expiry completes the existing engagement transition and synchronizes both pilots. Space-session close, ship death, and Abyssal participant death also close active module activities (`SpaceSessions.Modules.cs:576-595`, called from `SpaceSessions.cs:1546`, `SpaceSessions.Death.cs:436`, and `SpaceSessions.Abyssal.cs:99`).

Against the pre-fix runtime, the registered Crimewatch Host regression remained at active weapon timer state `101` with no expiry where the test expected finite state `102`. With the fix, the lost-end test leaves the activity open, advances the Host clock, refreshes the activity without recording another attack, and verifies expiry 60 seconds after the last refresh, persistence of the finite timer, and notification order. A PostgreSQL-backed `WeaponHostTests` test delivers `SimModuleActivityRefresh` through `SpaceSessions` and confirms the existing timer stays active; other tests exercise session leave, actual session close, and ship destruction through `SpaceSessions` into Crimewatch and verify persisted deadlines. A Rust scene test verifies an active hostile web keeps running while emitting the heartbeat. In EveJS, an isolated temporary GameStore run moved client timer states from active `[101, 201]` to finite `[102, 202]` on scene disposal; `crimewatchState.js:3925-3980, 5056-5074` shows the corresponding active-effect and scene-tick cleanup.

The real graphical V24.01 client and live simulation timing were not checked; client-facing state and the new internal simlink message were checked through codec fixtures, scene tests and Host integration tests.
