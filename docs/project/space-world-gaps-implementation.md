### SW-04: deployment dynamic blockers

**V24.01 client.** `eve/client/script/ui/structure/deployment/deploymentEntity.py:50-64` creates the preview point from the ship ball and asks `GetDeploymentConflictForBalls` to evaluate `ballpark.GetBallsAndItems()`. The deployment blocker includes live ballpark state. The same client builds warp-in blockers in `eve/client/script/remote/michelle.py:1418-1427`; `ballparkCommon/parkhelpers/__init__.py:14-17` selects celestial-category balls of radius at least 90,000 m except wrecks. This includes eligible asteroid belts. Normal warp targeting has a separate exclusion, so the server now has a dedicated deployment warp-point predicate.

**EveJS.** `server/src/services/structure/structureDeploymentPlacement.js:250-300` gathers scene static and dynamic entities and appends client-parity warp-in points; `:417-423` uses that list when a scene exists. I directly invoked `resolveDeploymentBalls` with a synthetic dynamic scene entity. It returned that live entity. This isolated Node process had no loaded itemTypes table, so it did not verify the warp-in point output.

**eve.rs.** Added SimLink query `GetDeploymentBalls` (request kind 166, reply kind 167; protocol 101). Rust `Scene::deployment_balls` settles resident pilots and emits live system bodies, ships, wrecks, live asteroids, Abyssal traces, deployables and missiles, plus deployment-specific client warp-in points. An unloaded scene returns an error. The Host composition reads this query for deployment validation; `StructureAnchorAuthority` merges fresh scene balls with static and persisted candidates, replaces stale real-ball duplicates by item ID, and checks blockers with their radii. Query failure is returned as a failed placement instead of silently using an incomplete scene. The shared SimLink fixture generator now pins protocol 101 and covers both new messages for the Rust and C# codec tests.

**Regression coverage.** Rust test `deployment_ball_query_returns_live_balls_and_client_warp_in_points` checks dynamic scene balls, warp-in points and the eligible large-belt case. `DeploymentBallsCodecTests` checks the .NET SimLink wire shape. Registered Host test `Structure_anchor_rpc_rejects_a_location_inside_the_client_moon_clearance_and_preserves_the_item` checks static moon/gate/belt cases and a blocker that exists only in the live scene.

The first end-to-end CI run exposed a stale live-walk assumption: it tried to anchor an Astrahus about 1.4 km from the current ship. V24 passes current ballpark objects into the deployment conflict check, and EveJS includes dynamic scene entities, so the ship correctly blocked the placement. The walk now asserts `CantDeployBlocked` with the current ship type, verifies that the item and structure state are unchanged, then anchors 100 km from the ship and continues the persistence/scene/notification/unanchor checks. This preserves the live-blocker behavior while keeping a successful end-to-end anchor scenario.

### SW-05: FW player kills

`FactionWarfareKillProducer` subscribes to the durable `ShipKillmailEvent` topic from the registered Host composition. The destruction event snapshots the victim's effective war faction at destruction; each attacking pilot's effective war faction and corporation are captured from the session when the damage ledger records that pilot. Legacy events without snapshots fall back to persisted direct/corporation/alliance state, honoring the recorded corporation/alliance downtime boundary. The producer identifies the final-blow pilot by killer ship ID and last-hit order, then counts only a hostile player kill in a mapped warzone. It writes pilot and event-time corporation daily kill rows in the event transaction. Friendly, non-warzone, NPC final-blow, self-kill, missing victim, and missing final-blow cases do not increment the rows. The registered Host PostgreSQL regression changes both characters' affiliations and moves the attacker to another corporation after durable publication but before delivery, confirms the event-time hostility and corporation still count once, and reopens the Host to verify its committed outbox cursor is not replayed.

V24 reads the daily totals through `facWarSvc.py` (`GetStats_Character` and `GetStats_Corp`, lines 340-363). The observed V24 victory-point UI reads/publishes VP state and vulnerability events (`fwVictoryPointSvc.py:31-69`). The player-kill producer records kill statistics only; it does not award system VP. EveJS `fwVictoryPointMgrService.js:92-143` and `fwQueryPayloads.js:13-51` cover VP state read/publish; no corresponding kill producer was found in the inspected EveJS runtime. The ship-kill LP award is still open.

### Control Bunker: lifecycle and SDE-derived scene placement

V24's Agency callsite (`eve/client/script/ui/shared/agencyNew/ui/contentPageInfoConts/factionWarfareSystemInfoContainer.py:49-60`) asks `GetControlBunkerIDInSystem`, then reads the returned inventory item and ball. It does not describe how the ball is positioned. The matching SDE build 3396210 has the unpublished group 925 `FW Infrastructure Hub`, faction-specific types 29286 (Amarr), 29302 (Caldari), 29303 (Gallente), and 29304 (Minmatar), and dogma attributes used for faction and hull state; it has no per-system bunker instances or position table. V24's reserved item range is `inventorycommon/const.py:71-72`. CCP's [Empyrean Age announcement](https://community.eveonline.com/news/news-channels/press-releases/factional-warfare-erupts-in-eve-online-with-launch-of-empyrean-age-1/) confirms the System Control Bunker role, and the [Inferno patch notes](https://www.eveonline.com/news/view/patch-notes-for-inferno) say those objects were renamed Infrastructure Hubs, but neither gives placement coordinates. EveJS's inspected faction service publishes victory state, but provides no Control Bunker spawn/capture runtime.

The Host persists a stable ID and pending-capture state, handles `SimStructureDamaged` hull depletion for a known group-925 bunker, schedules the next downtime, applies the occupier/VP/LP reset transaction, and publishes a post-commit capture event. Complex and battlefield results update a live bunker state and send the V24 vulnerability notices. On scene entry it restores the occupier's group-925 type and SDE hull attributes. `GetControlBunkerIDInSystem` returns a `PyLong` only when the stored item ID resolves to an actual live group-925 scene ball.

**Placement is an implementation inference, not a published FW coordinate rule.** V24 computes a sun warp-in point from the sun radius and position in `eve/common/script/sys/eveCfg.py:1467-1472`; EveJS uses that point for a Sovereignty Hub and offsets it by 100 km on Y (`server/src/services/sovereignty/sovHubPlacement.js:10-18`). The CCP [map-data guide](https://developers.eveonline.com/docs/guides/map-data/) describes celestial positions relative to the solar-system center, and the pinned `mapStars` row supplies the system's sun radius. With no FW-specific position source, the Host derives the stable group-925 anchor from this client calculation and the EveJS hub offset. This gives normal scene-entry spawn and capture re-spawn without a fixed packet coordinate or test-only provider; it does not prove exact live-server FW placement parity. The Host PostgreSQL lifecycle regression now reads the pinned SDE star and asserts the derived coordinate through initial placement, idempotent restore, hull depletion, downtime capture and replacement. The headless FW capture walk also checks the registered Agency RPC returns the live bunker ID after arrival.
