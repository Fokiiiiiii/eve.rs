# Oracle provenance

The golden fixtures and the JS benchmark baseline in this directory are
**generated from the EVE.js reference implementation** and copied here. The
generators stay in the EVE.js repository (they `require` its modules), so this
repository only carries their output.

| Item | Source |
|---|---|
| Source repository | `Fokiiiiiii/evejs-v0.12.9`, branch `ccr-fd6b2132-4353h1` |
| Source commit | `70ea5d807a328fa6d00bf07c2fb6a24ddea5e816` |
| `fixtures/marshal/cases.json` | `node tools/oracle/marshalFixtures.js --write` (543 cases) |
| `fixtures/destiny/cases.json` | `node tools/oracle/destinyFixtures.js --write` (4758 cases) |

To refresh from a newer reference, run `oracle/scripts/sync-oracle.sh <path to
evejs checkout>`, review the diff, and update the commit above.

Fixture format (EJSON): see `tools/oracle/ejson.js` in EVE.js, and the Rust
reader in `crates/eve-oracle/src/js.rs`.

## Scenarios recorded from the running reference

`fixtures/scenarios/` are not generated by the JavaScript generators: they are what the running EVE.js reference
answered to the headless client (`tools/headless-client/scripts/record_character_scenarios.py`, against a reference
started by `tools/dev/ref-server.sh` on data built from SDE build 3396210; the reference is run with `tools/dev/ref-bigint-json.js` required, which makes `JSON.stringify` write the 64-bit integers its debug log passes it as numbers: without it the reference throws while it logs the answer of a ship's inventory and the client is told nothing, so the first recordings of `inventory.json` held `null` for what is in a ship). `referenceCommit` and `recordedAt` are in
each file. They pin what the client can see on the way from login to a session with a character; where eve.rs
deliberately differs, `docs/compat/DEVIATIONS.md` says so. `login_to_character.json` is the walk, `starters.json` what
each bloodline is given, and `skills.json` what the skill handler answers for a new character of each race (the three
calls that return the whole skill list share one copy, marked `{"$same": "GetSkills"}`), `character_info.json` what
`charMgr` and `account` answer for a new character of each race, and `stations.json` the reference's station record for
a sample of 62 stations (every 87th of the static data and two more), which the station names are checked against, and
`inventory.json` what the inventory broker and the bound inventories of a new character's hangar, station and ship
answer, `cargo.json` what the cargo hold of a ship does (stacks given, put in the hold whole and in part, stacked, taken back, refused when they do not fit; in space the hold, a stack jettisoned and the can opened), and `dogma.json` the answer of `dogmaIM.GetAllInfo` (ship, fitted modules, character, brain, state) for a new
character of each of the four playable races (with the three notifications sent after it), which the dogma engine's values
and the brain are checked against, and `fitting.json` what the client is sent when a module is taken out of its slot, taken
offline and put online again (the events and the items that moved), and what the reference answers to a module call it
cannot do, and `training.json` the skill queue of a Caldari and an Amarr character (starting a skill, saving, reordering,
pausing and resuming a queue, the errors it gives, stopping, the history, each with the events sent and the skill window
afterwards), recorded at the reference's own training speed, and `training_fast.json` the levels that finish while the client
watches or is away, which needs a reference started with `EVEJS_SKILL_TRAINING_SPEED=60000` (the file records the speed it saw,
and the replay is skipped by a server that trains at another).
and `undock.json` a new character leaving its station, being sent the solar system, flying and docking again (the ship
service's `Undock`, the ballpark bound for the system and `UpdateStateRequest`, the movement commands and `CmdDock`; each step
with everything the client is sent, the destiny actions opened),
`movement.json` the orders a ship in space is given (`CmdAlignTo`, `CmdOrbit`, `CmdFollowBall`, `CmdStop`, `CmdSetSpeedFraction`, repeats, a
target that is not there) with what the reference answers and sends, and `approach.json` a ship that flies out of docking range and is told to
dock (the reference makes it follow the station, gives the user error `DockingApproach`, does not dock it by itself, and docks it when asked
again in range; the file also holds the ship's distance from the station's surface every few seconds of the approach). Each is recorded
with no other player in the system: another ship would appear in the balls.
`warp.json` a ship warping to a planet two AU away (the update that starts the warp, every event until the ship is at rest with the seconds each arrived
at, the ship's distance to the warp's end every three seconds, and the messages for a warp that cannot be done).
`jump.json` a ship warping to the stargate of its system (11.7 AU away) and jumping: the update that starts the warp, every event until it is at rest with
the seconds each arrived at, `CmdStargateJump` and everything the client is sent for twelve seconds (the effect and the stop, `OnJumpQueueUpdate`, the objects
let go, `OnItemChange`, `OnJumpCloakUpdated`, the session change), then the ballpark of the next system bound and its state asked for. The reference draws
where the ship lands and where it appears at random, so those are bounds, not values (`crates/eve-space/tests/jump_matches_reference.rs`).
`others.json` two characters in one system (a watcher in space and an actor that undocks, binds, is given orders, stops, docks, undocks again and warps to a
planet): for each step what the actor was sent and what the watcher was sent, with the seconds each arrived at. It shows what the reference tells a ship of
another that comes, moves, warps off and docks (the ball and its numbers in one update, the orders as they are, the ship taken out of view 7 seconds into a
warp, in a `PackagedAction`) and that the newcomer's first `AddBalls2` lists both ships.
`target.json` two characters in one system by the same station (the watcher is locked, the actor locks): what each is sent, with the seconds each arrived at, as the actor
asks for its targets and its targeters, locks itself, a planet and something that is not there (`DeniedTargetSelf`, `DeniedTargetingAttemptFailed`, `TargetingAttemptCancelled`),
locks a ship still under its undocking protection (`CustomNotify`), locks the watcher (about 3.8 s, `OnTarget add` and the damage state to both, `otheradd` to the watcher),
the station (0.76 s), locks again, unlocks (`lost`, `otherlost`), gives a lock up, unlocks with a list, clears (`clear`, `otherlost`), sees a locked ship dock (`lost` when it has
docked), warps with the station locked (`clear` when the warp is entered), tries to lock in warp (`DeniedTargetSelfWarping`) and from 2 AU away (`TargetNotWithinRangeGeneric`).
`module.json` two characters in one system (the actor works its modules, the watcher looks on): the actor flies at full speed, starts its afterburner (the ship's mass and top speed and the effect in two destiny updates, the module's and the ship's attributes, `OnGodmaShipEffect`, and every half second the capacitor charge as it recharges), starts it again (`EffectAlreadyActive2`), stops it (the module keeps on to the end of its cycle: 6 s later the attributes are given back, `OnGodmaShipEffect` says it is off and the destiny update takes the effect off), stops it again (a message), and tries the gun with no target, with a target and no charge (`SafetyActivated`: the reference's safety, not the charge) and the miner on a ship and with no target. Each step holds what the actor was sent and what the watcher was sent, with the seconds each arrived at.

`weapon.json` one character in space with a rat beside it (`/npc 1 Blood Visionary`, the only target a pilot may shoot in the empire with the safety on): the pilot fires the gun (the Civilian Gatling Railgun, which needs no charge) at the rat before locking it (`That target is not locked.`), locks it, heals, fires (the special effect, the module's cost, cycle and range, `OnGodmaShipEffect` at the start and at every cycle, and for each shot `OnDamageMessage` with `attackType` `me` and the target's damage state), fires again (`EffectAlreadyActive2`), stops the gun (the numbers, the effect off and the special effect at the end of the cycle; again: `<module> is not active.`), and fires and lets the lock go while the gun runs (the gun stops at once: the special effect off, the numbers, `OnGodmaShipEffect` off and then `OnTarget` lost). The rat is the reference's own (its AI, not the simulation's trees), so only what concerns the pilot's gun is compared. Each step holds what the pilot was sent, with the seconds each arrived at.

`ammo.json` one character docked with a gun that takes charges (the Civilian Miner is taken out with `/unfit me` and a 125mm Railgun I fitted with `/fit me`; `/giveitem Antimatter Charge S 500`): the pilot asks for its ship with the gun empty, loads the gun (`OnChargeBeingLoadedToModule`, the stack, `OnGodmaPrimeItem`, the rounds in the slot as attribute 805 of `(ship, flag, type)`, the changed range of the module, the items again), loads it again (nothing), lists its hangar, asks for the ship with the gun loaded (`GetAllInfo`: the charge by its item and by its key, the rounds in `shipState`), unloads the gun, loads it for the flight, is given three rounds of Iron Charge S and loads them in the place of the antimatter (the antimatter goes back to the hangar), undocks, calls a rat (`/npc`), locks it, heals and fires the gun until the three rounds are spent (`OnModuleAttributeChanges` of 805 at each shot, the gun stopped with `OnGodmaShipEffect` off) and fires it with nothing in it (`NoCharges`). The rat is the reference's own, so only the pilot's gun is compared in space. Recorded with `scripts/record_character_scenarios.py --only ammo` from the reference commit `b637d2a`.

`missile.json` one character with a Rocket Launcher I in the place of the Civilian Miner (`/giveskill me Missile Launcher Operation 1`, `/giveskill me Rockets 1`, `/giveitem Scourge Rocket 3`, `/unfit me`, `/fit me`): the launcher loaded in the station, then in space with a rat (`/npc 1 Blood Visionary`) locked and the pilot closing in on it (`CmdFollowBall`, `/heal` as it goes: the rat hits harder than a rookie ship takes) until a rocket is in reach, then `Activate` with `missileLaunching` fires the three rockets (each launch is one `DoDestinyUpdate` with `AddBalls2` of the missile, a ball in mode `MISSILE` with its slim item, and `LaunchMissile`; the combat log of each rocket that lands with `hitQuality` 3; `RemoveBalls`; the stop of the effect is `OnGodmaShipEffect` off with `NoCharges` naming the launcher) and fires once more with nothing in it. The rat is the reference's own, so only the pilot's launcher and missiles are compared. Recorded with `scripts/record_character_scenarios.py --only missile` from the reference commit `b637d2a`.
`drone_flight.json` one character with a drone (`/giveitem Hobgoblin I 1`, put in the drone bay) in space with the smallest armed rat (`/npc 1 Petty Thief`): the drone launched (`ship.LaunchDrones`), the rat locked and the drone sent at it (`entity.CmdEngage`, the ship mended every two seconds as the rat shoots it), brought home (`CmdReturnHome`) and into the bay (`CmdReturnBay`). Each step holds the answer (or the error) and what the pilot was sent, with the seconds each arrived at: the drone's ball and slim item, `OnDroneStateChange` / `OnDroneActivityChange`, the orbit, the drone's laser and the damage, the bounty, the item moves. Made by `scripts/record_character_scenarios.py --only drone_flight` (reference commit b637d2a). The drone kills the rat in one cycle: the recording holds the whole way from launch to scoop but only one engagement; the AI of a drone that is attacked while idle (state 6 against a rat that shoots) is in the first steps.

`reload.json` one character with a gun that takes charges (a 125mm Railgun I in the place of the miner, loaded in the station with 40 more antimatter put in the hold), then in space with a rat beside it (`/npc`): the gun unloaded into the hold (the stack that got bigger as `OnItemsChanged` to the character, the rounds in the slot), loaded from the hold (the reference makes the pilot wait the reload time: `nextActivationTime` and `OnChargeBeingLoadedToModule` at once, five seconds later the stack that got smaller, the charge primed, its rounds, the range and the module ready), loaded when it is full (nothing), most of the rounds taken out and the gun fired until the rest are spent (it stops with `NoCharges` with more in the hold: the turret does not reload by itself), fired while it waits for a reload with nothing in it (`NoCharges`), and fired while it tops up (it goes on firing and has its rounds when the time has run). The rat is the reference's own, so only the pilot's gun and hold are compared. Recorded with `scripts/record_character_scenarios.py --only reload` from the reference commit `b637d2a`.

`drones.json` one character in its station with two drones (Hobgoblin I) and some tritanium given (`/giveitem`): the drone bay (flag 87) of its ship asked for when empty and for the room in it (the rookie ship holds one drone: 5 m³), a drone put in it (a stack split, the new stack is the answer, two `OnItemChange`), the bay asked for, a second drone refused with `NotEnoughDroneBaySpace` (`type`, `free`, `required`), tritanium refused with `Only drones can be placed in the Drone Bay.`, the drone taken back to the hangar and put in again whole; then in space the bay (the reference also tells `OnGodmaPrimeItem` and `OnItemChange` for the drone the first time it is listed) and the room in it. Recorded with `scripts/record_character_scenarios.py --only drones` from the reference commit `b637d2a`.

`loot.json` one character with tritanium (100) and pyerite (60) put in the hold of its ship in the station (`/giveitem`), then in space (the reference's own rats shoot it meanwhile, which is noise): both stacks jettisoned in one `Jettison` into one can, the can opened and asked for its room, and everything taken at once with the loot window's call (`invbroker` `MultiAdd` on the ship's inventory: the two item ids, the can, `flag=5`; the answer `True`, `OnItemsChanged` for each stack with no place for the loot window, the can's slim item told for each stack, the single `OnClientEvent_MoveFromCargoToHangar`, the single `OnWreckLootAll` and the empty can going to the junkyard), then the hold, the room in it and the can asked for again (the can is gone: an empty list).

`health.json` one character damaging and healing its ship (`/dmg` in the hangar is the reference's only way to hurt a ship on demand; in space it refuses, "Dock first…"): the docked ship asked for whole (`GetAllInfo`: the ship's damage as a fraction, its capacitor, shield and armor in points, and the modules' own numbers) as new, after a light `/dmg`, after a heavy one and after `/heal`; the events each command sends (`OnItemChange` and `OnCfgDataChanged` for the ship and its modules; a heal adds an `OnModuleAttributeChanges` for each hurt module); the undock with the ship damaged heavily (its shield and capacitor are full in space and its armor and hull are as they were: the damage state in the destiny stream is `((1.0, tau, time), 0.4, 0.65)`); the ship asked for in space; and a `/heal` in space (the ship's armor and hull, `OnDamageStateChange` to everyone who sees it, the capacitor and the modules). The last steps also hold what an NPC of the system did to the ship (`OnDamageMessage`, the shield charge every half second as it recharges): not compared, the evidence for the NPC slice. Each step holds the answer (or the error) and what the client was sent, with the seconds each arrived at.
`--only walk|starters|skills|info|stations|inventory|dogma|fitting|training|training_fast|undock|approach|movement|warp|jump|others|target|module` records one and leaves the others as they are.

`fixtures/simlink/messages.json` is not from the reference: it is what `tools/dev/gen-simlink-fixtures.py` writes, the golden
frames of the link between the service host and the simulation (`docs/adr/0007`), a third writer of the format that the Rust
simulation (`crates/eve-space/tests/simlink_fixtures.rs`) and the C# host replay.

`crates/eve-space/data/undock_points.json` is not a recording: it is the reference's table of where a ship comes out of each type of station
(its `stationGraphicLocators`, made from the client's graphics), reduced to the undock points by `tools/dev/extract-undock-points.py`. The SDE
does not have it. It is used as data; none of the reference's code is copied.

## Wreck types

`fixtures/wrecks/ship_wrecks.json`: the wreck the reference's `resolveShipWreckType` (`server/src/space/wreckUtils.js`) gives the published ships of the
static data and a sample of the NPC ships (424 types), made by `tools/dev/gen-ship-wrecks-fixture.js` (it loads the reference from `EVEJS`, see its
header). The Rust port `crates/eve-space/src/wreck_types.rs` (ADR 0009) is held to it by `crates/eve-space/tests/wreck_types_match_reference.rs`.

## NPC hull weapons

`fixtures/npc/hull_weapons.json`: what the reference's `npcEquipment` (`getNpcWeaponModules`, `buildNpcWeaponModuleSnapshot`: `server/src/space/npc/npcEquipment.js`,
`server/src/space/combat/weaponDogma.js`) makes of the weapon of every NPC ship type of the static data that has one (4446 of 4687 types) and of one in twelve of
those that have none, with the attributes and effects of the type that it worked from (the reference's `getTypeAttributeMap`, `getTypeDogmaEffects`), made by
`tools/dev/gen-npc-armament-fixture.js`, and, for every NPC type that launches missiles (`missileLaunchingForEntity`: 1878 types, 693 with no turret), the missile the reference makes of it
(`getNpcEntityMissileWeaponSource`) with the attributes of the missile type it worked from (`missileTypes`). The C# port `dotnet/src/Eve.Npc/NpcArmament.cs` (ADR 0009) is held to it by `HullWeaponFixtureTests`. The simulation
knows one weapon to an NPC ship (its module is the ship), so 117 types that the reference gives two turrets (`targetAttack` and `targetDisintegratorAttack`) are
compared on the first, and the 18 types of the chain-lightning vorton projector have none.

`fixtures/npc/spawn_plans.json`: what the reference's `resolveNpcSpawnPlan` (`server/src/space/npc/npcSelection.js`, with `npcData.js` and `npcHullDamageability.js`) makes of 1838 queries after `/npc` (every pool's id, name and aliases, and a sample of the profiles' ids, names, upper-cased names, first aliases and parts of names, with the amount and the numbers a pool roll was given: which profile or pool, the error and the suggestions, the profiles rolled), made by `tools/dev/gen-npc-selection-fixture.js` from the authored tables only (the code-generated catalogs of the reference are switched off in it) with the ship types that have no hit points. The C# port `dotnet/src/Eve.Npc/NpcSelector.cs` is held to it by `SpawnPlanFixtureTests`.

`dotnet/src/Eve.Npc/Data/npc_authority.json` is not a recording: it is the reference's authored NPC tables (`tools/DatabaseCreator/staticTables/npcProfiles`, `npcLoadouts`, `npcSpawnPools`, `npcLootTables`: 5620 profiles, 112 loadouts, 83 pools, 61 loot tables) reduced to the fields the host reads by `tools/dev/extract-npc-authority.py`, with the 64 pirate regions (`PIRATE_FACTION_BY_REGION_ID` of the reference's `pirateFactionPolicy.js`, read by a pattern) the belt rats are placed by. It is used as data; none of the reference's code is copied. `dotnet/src/Eve.Npc/BeltRats.cs` is a port of the rules of `beltRatRuntime.js` and `pirateFactionPolicy.js` (ADR 0009), naming its sources at the top; `oracle/fixtures/simlink/messages.json` (version 6) is written by `tools/dev/gen-simlink-fixtures.py` as before.
