# EveJS 261108.1 Port Review: Empire Station and Gate Sentry Guns

Scope: compare eve.rs with EveJS 261108.1, the V24.01 client build 3396210, and the pinned SDE build 3396210. This record separates sentry behavior that already existed from the range and offense-trigger changes in this port. The graphical client and live Tranquility were not exercised.

## Verified game rules and client boundary

- CCP's [Criminal Timer](https://support.eveonline.com/hc/en-us/articles/203268591-Criminal-Timer) says gate and station guns fire on criminals in high security space, including a criminal entering high security space with an active timer. It also says low security criminals draw sentry fire but not CONCORD.
- CCP's [Suspect Timer](https://support.eveonline.com/hc/en-us/articles/203268571-Suspect-Timer) says CONCORD and gate guns do not defend a suspect from other players. CCP's [Retribution patch notes](https://www.eveonline.com/news/view/patch-notes-for-retribution-1) specify the sentry trigger more narrowly: a security-status penalty incurred nearby; sentry aggression is cleared after leaving the vicinity; drones are not targets.
- CCP's [118.6 patch notes](https://www.eveonline.com/news/view/patch-notes-for-118-6-release) add a low-security exception for fighters: after a character incurs a security-status penalty on the same grid, sentries may shoot that character's fighters for five minutes if they enter sentry range. EveJS 261108.1 and eve.rs currently only select the offending ship for sentry response; this fighter-specific rule is a known gap outside the behavior added by EveJS 261108.1 and is not claimed as implemented by this port.
- A whole-tree search of `/home/user/eve-logic/eve/client` for sentry-gun, group, range, and Crimewatch references found the relevant V24.01 behavior in `eve/client/script/environment/spaceObject/repository.py:90-97` (render class mapping), `eve/client/script/environment/spaceObject/sentryGun.py:38-77` (display turret fitting), `eve/client/script/parklife/targetMgr.py:586-597,1162-1185` (client handling of `OnTarget`), `eve/client/script/parklife/targetMgr.py:1335-1352` (the player's target range), `eve/client/script/remote/michelle.py:1536-1542` (damage-state update handling), and `eve/client/script/ui/services/crimewatchSvc.py:195-209,348-359` (client display of criminal/suspect flags). These callsites cover presentation, player targeting, and separate target/damage-state handlers; sentry offense selection remains server behavior. The client-side target range is the player's own Dogma value, not a sentry AI range.

## Behavior already present in eve.rs

- `Scene::populate_empire_sentries` places the Empire sentries at stations and stargates when the scene is first populated (`crates/eve-space/src/pochven_population.rs:524-589`). Their layout, faction and type selection match the EveJS layout. The sentries are ordinary NPC ships in the shared simulation, not presentation-only scenery.
- Before this port, the sentry behavior selected targets through the common combat tree after local security-status loss or criminal-flag activation. It already used the common target and NPC weapon paths, and dropped targets that left its bubble (`crates/eve-space/src/brains/rats.rs:44-59`; `crates/eve-behaviors/src/monitors/combat.rs:464-564`; `crates/eve-space/src/targeting/lock.rs`). The missing behavior was a direct trigger for an applied local offense and correct SDE acquisition range.
- Host module activation already records Crimewatch state, applies security-status penalties, and sends state to the simulation; on undock or system entry, the Host restores an active criminal flag to the simulation (`dotnet/src/Eve.Services.Space/SpaceSessions.Modules.cs:541-574,605-638`; `dotnet/src/Eve.Host/Composition/SpaceComposition.cs:344-352`). Host Crimewatch separately schedules CONCORD for a high-security criminal, including one entering high security space (`dotnet/src/Eve.Services.Crimewatch/CrimewatchRuntime.cs:775-810`; `dotnet/src/Eve.Host/Composition/SpaceComposition.cs:480-485`; `dotnet/src/Eve.Services.Space/SpaceSessions.Npc.cs:708-790`). This port does not change CONCORD or low-security suspect rules.
- Sentry weapons use the normal NPC weapon and damage path. The existing scene regression checks sentry invulnerability, type and weapon statistics, lock and firing notifications, damage notification order, and target removal after leaving the bubble (`crates/eve-space/src/brains/rat_tests.rs:247-325`). The Host's CONCORD response test checks response hulls and the configured ship-loss transition (`dotnet/tests/Eve.Services.Space.Tests/SpaceServiceTests.cs:3284-3350`).

## EveJS 261108.1 comparison

- EveJS 261028.1 had the static Empire sentry layout but no Crimewatch-to-sentry attack runtime. EveJS 261108.1 adds `server/src/space/npc/empireSecurity/empireSentryRuntime.js:8-26,38-103`; `server/src/space/runtime/crimewatchAdapter.js:33-54` calls it after an applied offense, and `server/src/space/runtime/scene/sceneFeatureHooks.js:291-299` ticks it with the scene.
- The new runtime limits engagement to the same local grid, ships that are alive and not warping, and the sentry type's SDE `entityAttackRange`; it then materializes a native NPC and issues the ordinary NPC attack order (`server/src/space/npc/empireSecurity/empireSentryRuntime.js:19-26,61-103`; `server/src/space/npc/nativeNpcService.js:2554-2606`; `server/src/space/npc/npcRuntime.js:447-455`). The materialization and `WeakMap` offense-assignment design are not needed in eve.rs because its sentries already exist as normal simulation NPCs.
- EveJS begins sentry response from an applied local offense. Its runtime accepts only a successful applied offense from its explicit reason set, checks same-grid/range/alive/not-warping state, and issues an NPC attack order (`server/src/space/npc/empireSecurity/empireSentryRuntime.js:14-28,38-103`). That path alone does not cover a criminal entering high security space with an active timer. eve.rs retains the existing Host system-entry and active-flag path required by CCP's Criminal Timer guidance.
- A direct runtime policy check was run against EveJS `noteOffense` with the range and scene/controller dependencies stubbed: at 600 km it issued the sentry attack order; at 1,100 km it did not. EveJS's full server stack was not started, and its local static type tables were not loaded for this check.

## Ported correction

Pinned SDE build 3396210 `typeDogma` records for Empire sentry types 1194 and 3739-3743 all have attribute 247 (`entityAttackRange`) equal to 1,000,000 m (records at lines 507 and 2064-2068 of `.cache/sde/eve-online-static-data-3396210-jsonl/typeDogma.jsonl`; attribute name at line 197 of `dogmaAttributes.jsonl`). Their turret `maxRange` is 500,000 m and `falloff` is 50,000 m. Target acquisition range is therefore distinct from weapon damage range.

Before this correction, the NPC's `max_target_range` was already 1,000 km but its behavior-tree attack range was 550 km, and the generic 300 km ship-lock cap also prevented its AI from completing longer locks. The sentry behavior now uses the SDE attack range, and only group 99 sentry AI bypasses the ordinary player-ship lock cap (`crates/eve-space/src/pochven_population.rs:38-40,89-100`; `crates/eve-space/src/brains/rats.rs:44-56`; `crates/eve-space/src/targeting/lock.rs:1-23`). Ordinary ships and structures retain their existing caps.

The regression `an_empire_sentry_acquires_a_criminal_within_its_sde_attack_range` uses a populated scene and asserts a lock, `OnTarget`, and turret FX at 600 km, then no lock or those notifications at 1,100 km (`crates/eve-space/src/brains/rat_tests.rs:328-365`). `a_gate_sentry_acquires_a_local_offender_within_its_sde_range` places a stargate away from the station and asserts that its own sentry locks and fires at 600 km (`crates/eve-space/src/brains/rat_tests.rs:408-461`). The 600 km cases prove acquisition and firing start only; they do not assert damage beyond the turret's optimal plus falloff. The existing near-range test covers sentry damage.

## Ported offense trigger

The live Host test first reproduced the gap: the attacker completed a low-security illegal shot and Host Crimewatch state was emitted, but no station sentry sent `OnTarget` at 600 km within 25 seconds. eve.rs now subscribes the existing sentry combat monitor to a dedicated internal event. The Host reports an `Attack` only when its outcome is `Criminal` or `Suspect`, after the security-status penalty callback (`dotnet/src/Eve.Host/Composition/SpaceComposition.cs:538-545`; `dotnet/src/Eve.Services.Crimewatch/CrimewatchRuntime.cs:356-365`). Lawful attacks, no-crime outcomes, and attacks on already flagged targets have other outcome reasons and do not enter this path (`dotnet/src/Eve.Crimewatch/Aggression.cs:71-84`).

`SpaceSessions` reports only to the matching active pilot in the same public solar-system scene (`dotnet/src/Eve.Services.Space/SpaceSessions.EmpireSentry.cs:7-18`). SimLink kind 161/protocol 95 carries the session ID; the Rust scene resolves the offender from authoritative pilot state, deduplicates the pending offense, and sends it to the existing combat monitor (`dotnet/src/Eve.Space/SimCodec.Shared.cs:27`; `crates/eve-space/src/link/kind.rs:19-20`; `crates/eve-space/src/scene/mod.rs:956-967`; `crates/eve-space/src/brains/world.rs:182-197`; `crates/eve-behaviors/src/monitors/combat.rs:464-556`). The monitor still requires the offender to be in its bubble and inside the behavior's SDE range. This adds no client RPC or notification shape.

The live regression `test_host_crimewatch_drives_station_sentry_fire_600km_from_the_station` runs two pilots through the real Host, front, simulation, and PostgreSQL on `eve_p4` (`tools/headless-client/tests/test_empire_sentry_live.py`). At a measured 600 km from station sentries, it verifies Host security-status notification, sentry `OnTarget`, that firing sentry's turret FX followed by positive `OnDamageMessage`, the attacker's damage-state update, and persisted Security Status history/transaction attributes plus suspect flag. The attacker stays outside the player's 300 km lock cap. Multiple sentries can lock the same offender; the test associates FX and damage with the firing sentry and checks that the first sentry target event precedes the aggregate ship damage-state update. Because `OnDamageStateChange` carries the ship ID but no shooter ID, it checks aggregate state after the earliest sentry target rather than pairing it with one sentry. V24 handles `OnTarget` and `OnDamageStateChange` in separate client handlers (`targetMgr.py:586-597`; `michelle.py:1536-1542`).

## Not ported

- The EveJS `WeakMap` offense ledger, native-NPC conversion, controller allocation, and per-sentry assignment bookkeeping are rejected as implementation techniques: eve.rs already owns persistent sentries and combat state as ordinary simulation NPCs. This port reuses those shared owners and adds only an internal Host-to-sim offense signal.
- The CCP 118.6 fighter exception is verified gameplay but is absent from EveJS 261108.1's ship-only offense runtime and is not covered by the range correction. It remains a separately tracked sentry-targeting gap; this record does not mark fighter response complete.
