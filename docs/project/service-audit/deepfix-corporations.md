# Corporation deep-fix handoff

## Archived application race

Client eve-logic/eve/client/script/ui/services/corporation/bco_applications.py:140-142 forwards application ID, character ID, corporation ID, application text, status, custom message (default empty) and application time (default None). UI callers include corp_ui_applications.py:437,749,831. The application consumer is bco_applications.py:31-34 and member-change consumer bco_members.py:58-61.

ApplicationAsync normally excludes archived records, so sequential RPC replay returns None. A concurrent request can pass that initial read before another archives the row. RespondAsync previously returned the archived row before actor or payload checks, and the service could notify and run the login hook based on the requested status. The store now checks actor and matching terminal status and payload under row lock and returns a per-call changed flag. The service suppresses replay notifications and login work, and reads actual membership after acceptance. The existing RespondAsync API remains available.

PostgreSQL eve_terra: dotnet test dotnet/tests/Eve.Corporations.Tests --filter FullyQualifiedName~Archived_application_replays_require_authority_and_do_not_emit_notifications: 1 passed, 0 skipped. It exercises store authorization, status and payload mismatches, matching replay, ordinary RPC replay notification suppression, persisted application/member and session state. The race interleaving itself and fail-before for the corrected test were not run. This invokes the service directly, not a registered Host wire route or graphical client.

## War declaration replay

Both corporation and alliance declaration replies now retain the original declared and started times after a same-operation retry; the corporation path suppresses repeat OnWarChanged as the alliance path already did. The existing bill row stores the original due time and does not update it during payment. The reply derives declaration and start from that persisted due time using the same seven-day and one-day intervals used when creating the bill. If those intervals change, persisted declaration/start timestamps should be carried explicitly rather than reinterpreting old bills. The original corporation store tuple API is retained.

The alliance clock-advance test failed before the fix because its returned time advanced by one second. After the fix the PostgreSQL tests Corporation_war_replay_keeps_original_times_and_does_not_renotify and Alliance_war_declaration_bills_are_replay_safe_and_pay_from_the_executor_wallet passed (2 passed, 0 skipped). The former calls the real store through a service callback and checks one bill, one creation and one notification; it is not a registered Host wire test. A concurrent retry was not exercised. dotnet build dotnet/src/Eve.Host --no-restore succeeded with 0 warnings and 0 errors.

## Corporation holdings and external shareholder reads

The corporation portfolio read previously filtered both shareholder and issuer to the caller's corporation, hiding shares that another corporation issued to it. `GetSharesByShareholder(1)` now reads all issuers for the authorized corporation. `GetShareholders` retains its existing own-corporation administrator check; an external issuer's shareholder list is available only to the active CEO of a live corporation that holds a positive quantity of that issuer's shares. The external authorization and returned rows are read in one repeatable-read transaction. The client uses these reads in `bco_shares.py:27-46` and `voting.py:166-177`. The pinned EVE.js implementation allows the external shareholder read, although its own portfolio response covers only the current issuer.

PostgreSQL `Corporation_share_rpcs_move_company_and_private_shares_without_changing_supply` failed before the fix because the foreign issuer was missing, then passed 1/1 with 0 skipped; it covers a real transfer, foreign portfolio and shareholder read, and non-CEO/no-holding denials. `CorporationSharesHostWireTests.Registered_corporation_share_reads_include_foreign_holdings_and_enforce_ceo_access` passed 1/1 with 0 skipped using real PostgreSQL, registered `CorpRegistryService`, encoded request and `PacketDispatcher`. This fixture constructs its own service registry and also verifies both owners’ notification payloads, add/update/remove, encoded call replay, recipient restriction and the before/after chain from concurrent administrative changes to the same issuer. The concurrent phase uses the store API rather than two encoded transfer calls.

Share mutations publish their old/new balances to the existing transactional event bus. The production Host registers the subscriber on the same corporation store before event delivery starts; notifications target the individual shareholder or authorized officers of the shareholder corporation, avoiding corruption of another corporation’s portfolio cache. `CorporationSharesCompositionTests.Host_composition_share_transfer_notifies_owner_once_and_replay_has_no_event` passed 1/1 with 0 skipped against an isolated cloned PostgreSQL database and actual `HostComposition.BuildAsync`: the registered encoded transfer produced one owner notification and two outbox rows, and replay produced no new row. This is not a TCP or graphical client test. Subscriber callbacks occur after the event cursor commits, so notification delivery across a process failure or disconnected client is not guaranteed exactly once; reconnect/cache refresh and a real process restart were not tested.

## War eligibility and notifications

The shared Host provider checks active qualifying SDE Upwell types, deployed anchored control towers, customs offices using the current inventory owner, and live sovereignty claim/hub and skyhook data. Corporation members inherit the current alliance eligibility; player organizations must be live and non-NPC. It supplies corporation public/registry info, lookup warPermit, and both war-declaration paths. New declarations are refused if either side is ineligible; member corporations cannot declare or be targeted independently. A known client-supported CustomNotify conveys this refusal. Existing successful replay is resolved before new-declaration relationship checks. The client calls and caches these fields in eve-logic/eve/client/script/ui/services/wars/warPermit.py:20-25,31-50 and selects alliance and HQ in eve-logic/eve/client/script/ui/shared/neocom/corporation/war/warDeclare.py:194-199.

OnAllowWarUpdated is sent after retryable event delivery recalculates current values. Structure state and alliance affiliation events, customs inventory owner changes/deletion, sovereignty journal changes, and tower anchor/removal publish the necessary events. The sovereignty journal observer uses the same transaction as apply and recovery, assembles actual grouped RowCodec rows, and registers before recovery. Tower anchor is notified by its scheduler job; authoritative deployed-row removal and its event share a transaction. Tower simulation and drop side effects were already separate from that transaction.
