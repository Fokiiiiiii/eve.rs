# EveJS 261108.1 Crimewatch comparison

Checked: 2026-11-10. Scope: CONCORD response delay, the criminal timer (often called GCC), suspect timer, limited engagements, security-status loss, and active offensive-module timers. The client source checked is V24.01/build 3396210 in `/home/user/eve-logic`.

## Verified in the client and current eve.rs

The V24 client defines timer states and durations in `/home/user/eve-logic/crimewatch/const.py:8-38`: weapons active/idle/countdown are 101/100/102 and 60 seconds; PvP are 201/200/202 and 15 minutes; criminal/suspect are 301/302 while active and 303/304 while counting down, both 15 minutes; limited engagements use `-1` while ongoing and otherwise last five minutes. The client stores timer state and expiry from notifications in `eve/client/script/ui/services/crimewatchSvc.py:222-250,262-288`. Its timer widget treats active states as no-expiry and treats any LE value of `-1` as ongoing in `eve/client/script/ui/crimewatch/crimewatchTimers.py:360-424`.

Whole-client searches for Crimewatch timer constants, timer notifications, CONCORD response timing, and security-penalty calculations found client consumers, not a client-side response-delay table or security-loss equation. For example, session changes load `GetClientStates` and cache its values at `eve/client/script/ui/services/crimewatchSvc.py:94-123`; the same service asks `DoesConcordReact` when deriving the minimum safety level at `:401-420`. Thus the wire states, expiries, LE sentinel, and system effects are client-visible requirements, but the exact CONCORD seconds and penalty equation are not derivable from client code alone.

Before this change, eve.rs already had the 60-second weapons, 15-minute PvP/criminal, five-minute NPC/disapproval/LE durations, ordinary criminal/suspect countdown states, LE persistence/expiry notifications, security-loss transaction persistence, and high-security criminal response. The response table at `dotnet/src/Eve.Services.Crimewatch/CrimewatchRuntime.cs:853-861` uses displayed security levels 0.9/0.8/0.7/0.6/0.5 for 6/7/10/14/19 seconds, matching EveJS 261108.1 at `/home/user/evejs-261108.1/server/src/services/security/crimewatchState.js:1406-1423`. eve.rs stores no distinct GCC field: its 15-minute criminal flag timer is the client criminal timer, and high-security CONCORD response is scheduled from it (`CrimewatchRuntime.cs:704-810`).

CCP support currently documents a 60-second weapons timer that starts counting down after aggression stops and the offensive modules deactivate ([Weapon and Logoff Timers](https://support.eveonline.com/hc/en-us/articles/203208932-Weapon-and-Logoff-Timers)); 15-minute suspect and criminal timers ([Suspect Timer](https://support.eveonline.com/hc/en-us/articles/203268571-Suspect-Timer), [Criminal Timer](https://support.eveonline.com/hc/en-us/articles/203268591-Criminal-Timer)); and five-minute LEs renewed by combat ([Duels & Limited Engagements](https://support.eveonline.com/hc/en-us/articles/203268611-Duels-Limited-Engagements)). CCP says high-security criminal timers trigger a CONCORD response but does not publish the ordinary security-level delay table in those articles. Its Triglavian-response article also documents effective response times changing with system conditions ([Effective security response](https://support.eveonline.com/hc/en-us/articles/360013963260-Effective-security-response-with-heightened-Triglavian-presence)).

## Ported: active module lifetime

eve.rs previously began finite 60-second weapons/PvP/criminal countdowns at aggression and had no active module state in `GetClientStates`. That could show a running module as a countdown, and a limited engagement could expire during continuous combat. EveJS 261108.1 tracks committed offensive modules, holds client timer states 101/201/301/302 without expiry, reports LE `-1`, and resumes countdowns when the last relevant module ends (`crimewatchState.js:3925-3982`; its scene disposal path ends the activities at `:3953-3961`). The real client explicitly treats these active states and LE sentinel as unbounded timers, as above.

eve.rs now associates accepted offensive modules with their attacker/target in `dotnet/src/Eve.Services.Space/SpaceSessions.Modules.cs:519-535`, connects that path in `dotnet/src/Eve.Host/Composition/SpaceComposition.cs:341-345`, and ends each activity on the simulation's `SimModuleEnded` at `dotnet/src/Eve.Services.Space/SpaceSessions.cs:1207-1221`. `CrimewatchRuntime.cs:385-555,899-939` keeps the active state, refreshes persisted deadlines once per second, and resumes finite expiries when the last module ends. It preserves a LE as ongoing while any relevant module runs and sends the matching stop/start-timeout notices in the transition order the client consumes. The registered Host RPC test checks wire tuples, `-1`, notifications, final FILETIME expiries, and persisted participant timers (`dotnet/tests/Eve.Host.Tests/CrimewatchHostWireTests.cs:234-344`); the real SpaceSessions/Pg test checks accepted module activation through the simulation end event (`dotnet/tests/Eve.Services.Space.Tests/WeaponHostTests.cs:23-105`).

The module activity itself is process-local. Its participant deadlines and LE expiry are persisted and refreshed while it runs; after a process restart, the persisted values are presented as finite countdowns, as tested by `RuntimeTests.A_restart_restores_persisted_module_combat_deadlines_as_countdowns`. EveJS likewise ends activities when a scene is disposed (`crimewatchState.js:3953-3961`). A forced process crash while a simulation remains alive was not separately reproduced.

## Compared behavior and decisions

### CONCORD response dispatch offset

EveJS subtracts `CONCORD_RESPONSE_TRAVEL_MS = 6_000` from the response table before dispatch (`crimewatchState.js:122-125,1426-1433`). Its comments say the table is a first-action time and the offset is based on Jita observations. In EveJS, that due time starts NPC responders from a distant anchor and begins their warp (`:3266-3341,4762-4833`). eve.rs's `ConcordResponseDue` event instead directly spawns the response pool 8 km from the offender at the due time (`dotnet/src/Eve.Host/Composition/SpaceComposition.cs:477-482`; `dotnet/src/Eve.Services.Space/SpaceSessions.Npc.cs:708-789`). These are different lifecycle points: subtracting six seconds in eve.rs would make the local spawn happen early. The client has no exact-delay table, and the source tree has no trace sufficient to verify a different TQ arrival time, so eve.rs retains its existing table and event timing. A real-client/TQ timing measurement remains unverified.

### Security-status loss equation

eve.rs already had the persisted penalty transaction and notification path (`dotnet/src/Eve.Services.Crimewatch/SecurityStatusPenalties.cs:48-112`), but used `previous + (10 - previous) * modification`. EVE University documents that equation ([Security status details](https://wiki.eveuniversity.org/Security_Status_Details)); its same-page statement that higher aggressor security status incurs the harsher loss conflicts with that equation for negative penalties. CCP's support article says standing losses use −10 as their target ([Standings, “The Math”](https://support.eveonline.com/hc/en-us/articles/203217152-Standings#h_01F1VZTHA3W1WMK0T9K99TAW3W)), and the Retribution notes describe security penalties as standing hits whose inputs include system security and the attacker/defender security-status difference ([Patch Notes for Retribution](https://www.eveonline.com/news/view/patch-notes-for-retribution-1)).

EveJS 261108.1 changed the multiplier to `10 + previous` and says consecutive negative values in `CONCORD.zip` distinguish the equations (`/home/user/evejs-261108.1/server/src/services/security/crimewatchState.js:2597-2608`). This makes the penalty move the status toward −10, matching CCP's documented standing-loss direction. The correction is ported in `dotnet/src/Eve.Crimewatch/SecurityPenalty.cs:4-33`. The new registered Host regression exercises the real aggression callback, persistence, `GetMySecurityStatus`, and `OnSecurityStatusUpdate`; starting at −0.25 against a zero-status target in 0.9 security, it asserts the result −0.4699 (`dotnet/tests/Eve.Host.Tests/CrimewatchHostWireTests.cs:147-265`). A direct unit regression covers the same equation (`dotnet/tests/Eve.Crimewatch.Tests/SecurityPenaltyTests.cs:25-36`).

The V24 client does not calculate security loss, and the referenced `CONCORD.zip` and its underlying TQ values are not present in the supplied trees. The raw trace and live TQ client were not independently inspected, so those checks remain open. The formula is supported here by CCP's standing-loss rule and Crimewatch penalty description, EveJS's cited trace, and the failing-then-passing end-to-end regression; it is not inferred from EveJS parity alone.

### GCC wording and scope

CCP's Criminal Timer article verifies the 15-minute criminal flag and its high-/low-security consequences. eve.rs applies those consequences through `Aggression.cs:58-85,175-237` and `CrimewatchRuntime.cs:704-810`; its exact high-security response table matches EveJS, while no additional separate "GCC" timer is needed for the V24 wire shape. The client's timer is the criminal timer state 301/303 (or 302/304 for suspect), not a separately named GCC tuple.
