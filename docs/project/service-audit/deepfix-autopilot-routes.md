# Autopilot, routes and jump correctness handoff

## Audited flow and client evidence

- Waypoints are character UI settings. `eve/client/script/ui/shared/maps/starMapSvc.py:2348-2446` writes and clears `autopilot_waypoints`; `2369-2376` reads it with default `[]` and discards the list if any destination is invalid. `2407-2420` builds a route from the current system plus those waypoints using the client pathfinder; `2638-2642` returns a copy of the locally derived autopilot route. The pathfinder wrapper delegates to its client implementation (`eve/client/script/util/clientPathfinderService.py:280-285`). There is no server waypoint RPC/state in this flow, so no server waypoint store was added.
- Whole-client consumers found by searching `GetWaypoints`, `GetAutopilotRoute`, and `autopilot_waypoints`: autopilot (`eve/client/script/parklife/autopilot.py:58-101,184,295,597,649`), route panel (`eve/client/script/ui/shared/infoPanels/infoPanelRoute.py:117,228-260,299,370`), settings (`eve/client/script/ui/shared/autopilotSettings.py:79,107`), navigation and map actions (`eve/client/script/ui/shared/maps/navigation.py:417,432`; `eve/client/script/ui/shared/mapView/mapViewNavigation.py:173`; `eve/client/script/ui/shared/mapView/selectedInfoCont.py:131`), fleet broadcasts (`eve/client/script/ui/shared/fleet/fleetbroadcastexports.py:64,86`), agency content (`eve/client/script/ui/shared/agencyNew/contentPieces/baseContentPiece.py:255,291`), location buttons and brackets (`eve/client/script/ui/control/statefulButtonLocationController.py:61,84`; `eve/client/script/ui/inflight/bracketsAndTargets/bracketVarious.py:113`), and nearby destinations (`eve/client/script/ui/shared/infoPanels/listSurroundingsBtn.py:242`). They read the same client-owned waypoint list or derived route.
- `autopilot.py:274-404` consumes the first derived path item, waits for a safe session/ballpark, selects the gate or celestial, and either approaches, docks, warps, or jumps. It calls the bound `CmdStargateJump(fromGate,toGate,shipID)` through `PerformSessionChange` at lines 343-363; the full client search found the other direct call at `eve/devtools/script/insider.py:630`. Autopilot warps through `AP_WarpToDestID` at lines 461-486, which first sets the client warp destination and then calls the server command. The user-facing jump error handling at `autopilot.py:422-442` stops on stuck/emanation/standing and selected structure errors, follows the gate again on `NotCloseEnoughToJump`, shows other `SystemCheck_JumpFailed_*` dialogs, and retries after five timer cycles.
- Client jump notifications are not a route reply: the autopilot call is wrapped in a session change, then displays the jumping prompt and scatters `OnAutoPilotJump` (`autopilot.py:343-363`). The client waits for session and ballpark consistency before another jump (`autopilot.py:274-326,388-420`). Client-local waypoints remain the source for the next hop after session change.

## Host, simulation and reference comparison

- Host exposes `CmdWarpToStuffAutopilot` and `CmdStargateJump` in `dotnet/src/Eve.Services.Space/BeyonceService.cs:704-723`. Autopilot warp is 10,000 m from the target (same file's dispatch body and `SpaceSessions.Movement.cs:270-292`); jump delegates to `SpaceSessions.JumpAsync` (`BeyonceService.cs:716-723`). `JumpAsync` checks ship/policy/gate rules, sends the sim command and sends `OnJumpQueueUpdate` after acceptance (`SpaceSessions.Movement.cs:313-369`). The later `SimJumped` completion persists the new location through `_ships.JumpAsync`, changes session attributes, and sends the item, jump-cloak and session notifications in order (`SpaceSessions.Movement.cs:442-529`).
- Route distances align with EVE University: stargate use requires being within 2,500 m ([Stargates](https://wiki.eveuniversity.org/Stargates)); autopilot warps to gates at 10 km and warp exits use a 2,500 m envelope ([Advanced Piloting Techniques](https://wiki.eveuniversity.org/Advanced_Piloting_Techniques), [Warp mechanics](https://wiki.eveuniversity.org/Warp_mechanics)). The sim enforces the gate range in `crates/eve-space/src/gate.rs:234-270`; autopilot warp passes 10,000 m in `BeyonceService.cs:704-713`. EVE University notes customs patrol in known-space gate systems ([Known space](https://wiki.eveuniversity.org/Known_space)); EveJS's completion hook gives the exact arrival point for this server transition. No distance formula change was needed.
- EveJS 261028.1 uses the same 10 km autopilot warp in `server/src/services/ship/beyonceService.js:4185-4208`. Its `Handle_CmdStargateJump` validates and accepts the jump, then returns `null` (`beyonceService.js:4283-4324`); its comments record the client call as session-change based and the reply as `None`. The V24.01 client does not read a gate RPC payload at its callsites above.
- EveJS runs customs inspection at completed gate arrival, after the destination transition is attached (`server/src/space/transitions.js:1775-1815,1980-2007`), not when the jump RPC is merely accepted. The EVEU customs/contraband mechanics are applied on entry to the controlled system; the executable reference confirms this arrival ordering.
- No pinned SDE values are involved in these paths.

## Fixes

1. Destination customs inspection previously ran in `JumpAsync` as soon as the sim accepted a stargate RPC, before the `SimJumped` event and persisted system move. A queued jump that did not complete could therefore confiscate cargo and emit item-change state while the pilot remained in the source system. The service now marks accepted stargate jumps, consumes and clears that marker in the shared jump completion path, and inspects only after a successful persisted arrival (`SpaceSessions.Movement.cs:354,442-444,523-534`; marker field `SpaceSessions.cs:74`). Wormhole, cyno, bridge and conduit arrivals leave the marker clear.
2. Host's `CmdStargateJump` returned the internal bound-object/cooldown tuple from `JumpAsync`; the V24.01 client does not read that return and EveJS returns `None`. Host now awaits the state transition request and returns `None` (`BeyonceService.cs:716-724`). The jump queue notification remains a separate notification.

## Regression evidence

- `SpaceServiceTests.A_gate_arrival_inspects_the_ship_in_the_destination_system_only_after_the_jump_succeeds` (`SpaceServiceTests.cs:2773-2809`) asserts no inspection on refusal or on RPC acceptance, then exactly one inspection after `SimJumped` moves the persisted session to the destination. Before the timing fix it failed at the post-acceptance `Assert.Empty(inspections)`; after the fix it passed.
- `WormholeJumpServiceTests.A_jump_into_a_system_with_an_environment_gives_the_simulation_the_ship_again_with_that_environment` (`WormholeJumpServiceTests.cs:156-184`) also asserts that the shared arrival path does not inspect cargo on a wormhole jump.
- `StargateJumpWireTests.Bound_client_warp_then_stargate_jump_uses_the_wire_and_clears_warp_state` (`StargateJumpWireTests.cs:61-93`) verifies warp reply `None`, queue notification before jump CallRsp, jump RPC reply `None`, 10 km warp args and gate args. With the corrected expected shape and before the Host fix it failed because the Host returned a tuple. The first run after the Host fix also exposed four direct service tests that still expected that tuple; those assertions now require `None`.
